## Reusable controllers and completion

Compose a result-menu controller trait with explicit information provider, action definitions/layout and a `showAfter` completion-scope reference. A stage-won definition references its bounded reward-presentation scope; a game-over definition references its stats-ready presentation. Generic renderer/navigation code dispatches those providers/actions and never branches on result/scene kind. Sources supply action data; they are not a side table keyed by scene identity.

Authoritative coins/cards/payment receipt/outcome are already committed. Row callbacks display captured entries and play their configured sound; they cannot award, generate or pay. When completion settles successfully or by configured reduced-motion/summary fallback, reveal/mount the choice stage exactly once for that generation. Cancellation on scene exit never reveals it later. A stale play outcome cannot replace a newer authoritative result. Required scopes are finite; ambient smoke/music never hold these choices forever. A failed visual sequence uses its captured final summary and exposes actions through the same bounded fallback contract, not an endless spinner.

The source audit found that `showStageWon` currently owns `rowTimers` and reveals its legacy button in the final timeout. These are migration gaps, not an existing public completion capability. The implementation must expose bounded completion through the shared scheduler and preserve that completion/mount contract; it must not copy those private timers into a second presenter or introduce a global busy flag. Scope any necessary ledger scheduling migration as a focused prerequisite if it cannot fit the menu PR.

## Stage Won layout and reusable control precession (#1057)

The reward ledger retains its readable HTML information panel. The Visit Shop word cube is a **sibling action presentation outside that panel**, with a transparent stage and no surrounding visible rectangle. Its inspection caption is owned by a separate viewport-bottom caption outlet, not by the ledger panel or the cube's local row. Position the caption above the bottom safe area, with readable wrapping and a reserved region so neither ledger nor action overlaps it. Keep the polite live-region semantics, but route one authoritative description to one visible caption; do not create a duplicate active menu.

The result-menu trait configures information provider, action-host layout, sizing and caption outlet as independent references. The generic host resolves those registered capabilities without knowing which result/action it is. Initial Stage Won tuning makes the Visit Shop cube **1.25 times its current apparent edge**, bounded by available space in narrow/short viewports. This is a reversible design default for “larger”, not a new global menu-size rule or permission to apply the title-only Dev13 scale everywhere. Prefer shrinking spacing/reflowing information over covering the ledger. Keep a readable gap between information, cube and bottom caption; on small viewports allow the information region to scroll without trapping or moving the caption offscreen. The action remains below the information in visual/focus order and appears only after bounded ledger completion.

Compose the same **ambient three-axis precession capability** on Visit Shop and the shop control blocks (#992/#1075). A trait owns a dedicated transform node between layout/spring placement and the inner interaction-feedback/artwork nodes. Only that trait writes its node. The layout/spring owns position/outer displacement, precession owns ambient orientation relative to a captured readable rest pose, and hover/press owns its inner offset/scale. Never overwrite one another’s Euler values or use action-name checks to pick a motion path. Existing beat kicks remain optional independent spring input; stock dancing (#774) is a different composed behavior and not a prerequisite.

The trait accepts configured rest orientation, per-axis angular amplitudes, period/phase offsets and reduced-motion policy. Initial readable rest pose: pitch 8°, yaw −12°, roll 0°; oscillation amplitudes 4°, 6°, 2° respectively; periods 72, 90, 108 game-time units (4.8, 6, 7.2 seconds). These bounded, different periods make depth visible without spinning a text face away. Compose bounded axis rotations in a fixed documented order relative to the rest quaternion; do not accumulate rotations into an unbounded drift. Phase is local ambient state, not model RNG or saved gameplay. Use the shared presentation frame/clock and freeze while covered; resume without catching up an unseen elapsed interval. Reduced motion holds the readable rest pose. Disposal removes frame subscriptions and releases only owned transform/visual resources.

Per-frame precession is ambient work, **not** a sequence on the finite visual-event scheduler and not another timer/clock. It never holds result scopes open. Ray hit testing and keyboard focus geometry follow the actual composed transform each frame. An invisible full-window canvas must not intercept unrelated gestures. Unavailable/disabled state, click sound, pointer/touch, long-press, keyboard and screen-reader activation remain the existing shared capabilities; all paths invoke the registered navigation command once.

**Source audit and reasoning.** `src/block-menu/block-menus.ts:createBlockMenus` creates its caption beneath the row and exposes `onInspect`; `src/block-menu/cube-stage.ts:CubeStage.setSizing/start` owns stage sizing and an animation callback. `src/scene-behaviours.ts:resultMenu` already mounts actions on a registered completion and disposes on cover/exit. `src/traits/spring-anchor.ts` owns an outer transform and only roll, while interaction feedback owns the inner node. These supply reuse seams but do not already implement a standalone three-axis motion layer or viewport caption/layout contract. `src/style.css` positions `.block-menu-caption` within the host. Moving only a CSS button or writing idle Euler angles into the spring node would leave the requested separation or composition unsatisfied; explicit host configuration and a dedicated motion node avoid those conflicts.
