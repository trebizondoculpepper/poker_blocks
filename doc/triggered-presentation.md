# Composable triggered effects and victim responses (#1168)

Design resolution for #510 and remaining #438 integration. Existing trigger, removal/resistance, exit recipes, dazzle and smoke foundations are reused. This does not approve normal-game bombs, change destruction/bonus rules or let a visual effect decide a secondary detonation.

## Use the actual trigger occurrence, not a victim proxy

`src/triggers.ts:commitTrigger` already emits **`block.triggered`** once for an accepted source, with its captured source/cell and causal path, before committing its configured responses. The shared chain guard prevents triggering the same source twice in that chain. A source with no neighbours still emits this fact. Therefore no new detonation fact or optional cause on `self-destruct` is needed merely to find the explosion origin. `block.removed` with an explosion cause is a victim outcome; using it as the only source cue would lose no-neighbour explosions and confuse victims with actual detonations.

A detonating definition composes a registered **on-trigger presentation response** as configuration, independently of its model `triggerable.responses`. A trait/definition response provider brings behavior: for the captured `block.triggered` occurrence it returns the configured effect reference, settings and source anchor descriptor. Generic projection code invokes registered providers uniformly; it never asks whether a block is a bomb, reads a `detonates` flag, inspects model command names or selects visuals from a material-name table. A triggered definition with no explosion response does not become a detonation merely because it was triggered. Ordinary destroyed victims emit their removal/destruction facts and do not generate another explosion.

The committed-action presentation controller resolves these response providers **at commit** from captured source definition/trait configuration. Produce plain immutable requests with action/event occurrence ID, captured source instance/appearance reference, source cell, causal path/depth, effect handler/config and a presentation generation. Copy only needed plain context; do not retain the trigger chain's mutable visited set or query the live field later. If location is unavailable, omit with a diagnostic instead of inventing the origin. Restore does not replay old triggers. Rollback/unaccepted triggers publish no committed request.

The effect service receives an explicit source anchor (captured board-local cell plus declared presentation parent transform), not `GameRun` or a callback that locates a card. The board/camera may continue moving visually through its presentation transform handle; model identity/ownership/material is never reread by the effect. Source self-removal does not erase its captured position or suppress the request. Deduplicate by occurrence, not material/sound ID or cell, so independent simultaneous sources remain independent.

## Causal source-first presentation

The root source effect starts at its action's configured post-score trigger-presentation boundary. Actual secondary sources receive their own captured request, with initial delay **two game-time units per causal path step** after the root. The causal path is already model-produced; the controller schedules all captured requests in stable fact order on the shared visual-event scheduler. It does not run a delayed blast command or discover neighbours from a later state. A non-detonating relay may be part of the path without a pop of its own. The configured spacing is reversible tuning, not a new gameplay delay.

Each explosion composes the existing dazzle pop and finite smoke burst: 3–6 white-centred/yellow-fringed pops, configured spread/variation and bounded smoke lifetime. Cosmetic choices use a captured cosmetic seed or controller-local cosmetic randomness, never session RNG in a delayed handler. Reuse #1037's range/color/burst capabilities, #493 dazzle and #464 smoke rather than another particle engine. Per-pop audio remains #520's shared registered path, exactly once per intended visual pop; source or victim removal callbacks cannot duplicate it.

Finite source/secondary/victim scopes belong to the committed action's phase response. Seal only after captured child work is registered; required action scopes settle under normal scheduler accounting. Ambient smoke tails cannot hold a result forever. Reduced motion/flash-safe settings use the existing softened dazzle and bounded smoke response; omission/overload/cancel has explicit diagnostics and no model effect. Scene teardown cancels once, releases resources and ignores late callbacks. New valid input is never blocked by the chain animation.

## Victim exit and survival feedback are separate capabilities

A **destruction-exit controller** consumes the registered authoritative removal/destruction outcomes appropriate to its configured cause policy. It requests the existing `resolvedExit` recipe from captured appearance data, retains the departing visual through the [captured-mount policy](visual-event-interface.md#captured-snapshots-and-missing-presentation-mounts-1161), and invokes the one shared exit presenter. Normal collection, unwrapping, reset and rejected destruction remain distinct facts, not inferred from a missing block. There is no second authoritative inventory or resurrection at effect completion. A source that self-destructs may have its ordinary exit visual alongside its independent positional explosion; those effects own different resources.

A **resistance-feedback controller** consumes `block.resisted`, preserving the live block and all bonuses. The definition supplies a registered appearance response (serializable recipe/provider, alongside its existing exit configuration), not a branch in a generic renderer. Steel and Gold definitions configure the already approved subtle flash/shudder; other definitions must explicitly supply feedback or a deliberate no-op response through the same capability. Generic code dispatches the resolved response, never tests resistant traits as flags or turns a survivor into an exit. Flash/shudder owns additive visual channels only, never grid coordinates. Keep original emission/material state and existing hover/pulse effects intact.

These two controllers may share a registered outcome-to-request projection and mount services, but remain independently composable. `appearance.exit` and assembly defaults already provide destructive recipes; they do not currently provide complete production victim integration or a uniform survivor-response binding. The new binding is a documented target, not a claim the closed per-material foundation tickets already wired gameplay. Missing required recipe/response is a composition/coverage diagnostic, not an invented fallback breakup. All registered admitted test materials must either resolve an approved response or report the specific missing design; do not silently add new material looks.

## Developer audition: real commands, explicit test composition

Use a **Dev-prefixed fixture trait/definition** composed only in a developer mode, with existing countdown/trigger propagation/destruction/self-removal handlers and the new on-trigger presentation response. This is an engineering fixture for already registered mechanics, not normal-game bomb acquisition. Its definition owns complete lifecycle, mass and provisional metadata; imports/registration stay under dev-tool composition and out of the production bundle. The mode's opaque identity is declared only in `game-modes.ts`; no tool or generic runner branches on that identity.

Exercise a lone source, mixed ordinary victims and resistant survivors, and a second configured detonating source. Use actual model commands and committed facts, not fabricated outcomes that bypass trigger guards/RNG/rollback. A fixture restart uses the same seed/setup. Model removal/resistance/secondary-trigger decisions are immediate; only visual causal spread is delayed. The ordinary victims must not each pop. The no-neighbour source must still pop. Existing exit/profiler cases can separately audition individual recipes; the mixed fixture proves production-style event/mount composition. No second audio catalogue or special synthesis room is added.

Preserve the card's real material, resistance and appearance; no synthetic clone material or generic material-name check. This fixture is composed only in developer modes and excluded from ordinary pools/build composition. It does not approve normal-game bombs.

A board-gesture handler recognizes double-click and touch double-tap through the shared use-gesture input path and issues the configured registered action against the picked opaque block handle. Reuse that normalized gesture for the existing manual-destruction tool; do not depend on a browser-synthesized mouse dblclick for touch, invent an independent pointer loop, or put mode tests in the adapter. Gesture thresholds are configured input policy, cancellation/lost capture releases its owner, and a drag/pinch must not accidentally detonate.
