# Shell-free Cloud / Steam card appearance

Owner-approved visual direction, 2026-11-15 (#1334, documentation #1368). Cloud and Steam are **one existing material/card**, not aliases that create two definitions. The `cloud` lookup identity, saves, stage retention, mass and scoring remain unchanged by this appearance decision. The separate reaction change is #1268.

## Visible contract

Keep the liked soft drifting cloud volume; remove the visible plastic/glass box, shell sheen, face fill and continuous cube-edge artwork. The cloud itself remains volumetric inside the ordinary card-sized interaction bounds. A cube-shaped sampling/support volume is permissible internally but must not read as a visible container. This is an appearance change, not simulation of expanding gas or a different placement shape.

Rank/suit float at their usual top-left positions within the virtual card faces, without a surface or rectangular backing. Acquired bonus text remains bottom-right and full inspection remains available. Reuse existing face-art layout, rank/suit colors/font and complete bonus descriptors; do not recalculate bonus values or reveal concealed payloads. A small configurable glyph halo/outline may provide contrast, but not a panel/opaque sheet. Render only appropriate outward-facing label planes under normal face visibility conventions so the same text is not layered through from rear faces. Preserve cube-local orientation; do not turn it into one global HUD label detached from its card.

Logical attach/hit/selection bounds remain the normal card cell and transform. The selection outline can disclose those bounds **when selected**; removing permanent edge artwork does not remove interaction feedback. Hover/focus/tap inspection still works even in transparent parts of the logical bounds. Do not let the raymarch's current density decide whether the card is pickable. Multiple nearby clouds must retain readable, individually associated labels; do not force every label on top of every foreground card to conceal a depth-order problem.

## Source evidence and reusable capability

Audit at main `1111027f`: `src/materials.ts` defines Cloud with `assembly: contained`, a `plasticShell`, the registered cloud contents and permanent edge opacity. `src/visual/cloud.ts` registers a soft-noise raymarch through a boundary volume, with drift driven by the contained update and no published liquid-surface capability. `src/visual/contained.ts:composeShellFree` already composes contents/residue/inclusions without a shell, but expects its caller to own face appearance. It does not by itself create floating rank/suit print or prove a shell-free Cloud has shipped. `src/visual/block-appearance.ts:BlockAppearance` separates face materials, extras, prepasses, mask and selection declarations; the current contained assembly/print owns face text. Existing hand/board/shared card mounts consume that contract.

**Target composition:** use a configured shell-free volume assembly and a separately registered floating-face-label capability. The assembly supplies the same existing cloud contents configuration through `composeShellFree`; the label capability accepts captured shared face art, logical face dimensions/insets, glyph contrast and ordinary face orientation. It yields transparent glyph-only materials/parts with explicit ownership, plus the existing pick/bounds and feedback descriptors. Other shell-free materials may compose the same labels without a cloud-name check. Generic views render declared parts/capabilities and do not hide a container by material ID or test a trait as a flag.

Configuration lives on the definition/appearance composition. Keep volume shader parameters initially unchanged to preserve the liked look. No separate clock, RNG or shader is introduced just to remove the shell. Registered frame/selection/transition-mask handlers cover every declared part; a transition/exit fades labels and volume together. Intrinsic labels remain unlit/readable according to the shared face-art convention, without making the cloud reflect as a shiny solid. Shared scoring-tint/pulse adopters must use appearance capabilities rather than assume glyph/volume shaders have color/emissive fields (#1361 is a separate concrete bug).

Owned label textures/materials are disposed once by their appearance lifetime; borrowed geometry/resources follow existing ownership. The original virtual bounds remain available to hit/outline and coordinate conversion without drawing an opaque cube. `composeShellFree` owns the interior's ambient update registration; no second per-frame ticking is added for labels. Scene exit, hand→field swap, material replacement, reduced motion and cancelled transitions release old parts/subscriptions and cannot leave a label floating after its card is removed.

A visible clear shell with opacity set to nearly zero would retain reflections/edges and contradict the owner. Replacing the volume with a flat sprite would discard the accepted look. A cloud-only text renderer would duplicate face-art/bonus layout and prevent reuse. Configured shell-free volume plus reusable glyph-only face parts is the smaller composable target. This is a source-backed recommendation, not rendered acceptance evidence; label/volume transparency and several overlapping cards need actual screenshots.

## Delivery and verification

Deliver #1376 reusable floating-face label/virtual-bound appearance capability first, then adopt it with shell-free Cloud under #1334 (the owner visual acceptance item). Neither waits for the changed boiling-water spawning rules, and those rules cannot be changed as part of this artwork PR. Existing explicitly contained cloud audition examples may remain container examples; they do not create a second gameplay Steam material. The certified production Cloud adopts the approved no-box appearance after this separate docs merge; keep generation/economy eligibility unchanged.

Verify hand, board, generic inspector and relevant icon hosts, all view angles, light/dark background, overlapping/distant cards, top-left identity/bottom-right bonuses, normal attach bounds and transparent hit areas, selected outline only when appropriate, frame drift, rendering/mask/exit compatibility, repeated mount/swap/disposal and bounded draw cost. Supply before/after images and a short rotation/overlap clip. Report any unsupported label/mask provider explicitly rather than replacing the cloud with an invisible object. The documentation does not claim those visuals or performance have been verified.
