# Source-settled drop outcomes (#1200)

This extends the [Input contract](game-architecture.md#input-284-epic-271) for the already agreed [return-source-then-invoke-action target](shop-control-blocks.md#continue-click-and-explicit-drop-action). It changes the protocol, not purchase, sale, discard, navigation or drag admission rules. Implementation follows this documentation in separate focused deliveries.

## Ownership and protocol

Keep collision/hover verdicts (`accept`, `reject`, no hit) separate from the release outcome. A target accepting a hit may commit a transfer, refuse at release because its rules changed, or request a successful return followed by its configured action. A requested return is not a refused transfer and must not play the denial cue or be traced as refused.

Use an explicit drop-outcome handler registry, keyed by protocol operation, never source, target, scene or item identity. The target returns a typed outcome carrying only the operation's configuration and one-shot continuation. Shared dispatch calls its registered handler with the active source's settlement capability. The input adapter does not interpret a navigation action or identify an offer/rack/hand. Existing boolean-returning targets may use a single compatibility adapter mapping success to committed transfer and failure to ordinary refusal; this adapter is transitional, not a parallel source-routing policy.

Each active source supplies a gesture-owned settlement handle: opaque generation, synchronous `returnToOwner()` result, and an idempotent close/invalidity boundary. The source's own handler restores its ownership/presentation references and clears its active carry before reporting success. Return succeeds only while that source still owns the complete captured carried group and can safely restore it; stale/disposed sources report failure without partial transfer. A source that cannot promise this must not admit the return-action capability. Admission is explicit configured capability wiring, not a trait tested as a flag or a side table of source names.

The return is a synchronous ownership settlement, not a Promise for the fly-back animation. Dragging ordinarily has not transferred model ownership, so no purchase, refund, sale, discard, card refill or save mutation is implied. A return may start its existing presentation, which can be cancelled by the ensuing scene exit. If a source needs atomic restoration, it validates the whole group before making changes; failure never authorizes the action. Do not invent a generic rollback by diffing game state.

## Return then act

The reusable return-action handler receives the captured settlement handle, a configured action's availability query and invocation handler, and the target's active registration lease. It consumes the release continuation once, asks the source to return, then rechecks that the target lease/generation remains active and the action is currently available before invoking that action once. Closing a consumed continuation before invocation prevents a re-entrant command or source callback from invoking it again. The source carry is already cleared when the action runs, so scene-exit cancellation cannot recursively settle the same drag.

Cancellation, lost capture, blur, source removal and cover/exit use the source's ordinary cancelled return path and never create an action continuation. A normal release with no target also returns without an action. Refused outcomes retain existing authoritative refusal feedback. If requested return fails, report refusal through the configured owner once and do not invoke; if action availability changes after successful return, leave the object returned and report the configured unavailable response once. Do not synthesize an extra click or register both a drop continuation and a second navigation dispatch. The command retains its existing action sound owner.

A target can disappear during the synchronous return callback, so availability alone is insufficient: the target registration lease must still be live. A subsequent gesture cannot consume an old continuation. Hover, hit regions and keyboard/touch drag semantics retain their existing owners; the manager only delivers lifecycle and dispatches registered protocol operations. No timer, animation wait, live-model read from a delayed handler, or input-busy flag is introduced.

## Adoption and evidence

Implement and test the protocol with controlled source/target handlers first. Adopt it separately in the existing hand/rack owner (`table-input.ts`) and shop-offer owner (`shop-view.ts`), preserving their existing transfer and return semantics. The shop Continue target is not ready for completion until every configured admitted source supports the protocol. A source outside that composition need not be migrated merely to finish this target; it must not silently become admitted. #1148 then implements the configured return-action target and #1079 composes it with Continue.

Source audit at `0c8f7f7`: `src/drag-drop.ts:DropTarget.drop` returns boolean and `DragSource.end` returns void. `src/table-input.ts:commitDrop` treats a hit that returns false as refusal, then calls `hand.putBack`; the target cannot observe successful return. `table-input.ts:rackSource.end` owns rack return/reorder/use/sale. `src/shop-view.ts:dragSource.end` owns offer restoration and purchase dispatch. These independently owned paths explain why calling a target after a false boolean, or branching on source names, is insufficient. This is a proposed shared protocol, not a claim that those sources already implement it.

A third string outcome alone would distinguish return from refusal but still lack source acknowledgement and re-entrant cleanup guarantees; the explicit settlement handle supplies those. Moving return policy into the manager would make it learn ownership details. Waiting for animation would violate model-first input and fail on navigation teardown. The registered outcome plus source capability keeps the extension composable and bounded; no new drag library is needed.

Verification covers transfer/refusal compatibility; no-hit return; successful and failed requested return; unavailable action before/after settlement; complete multi-card ownership; stale generations; duplicate release; cancellation/lost capture/blur; return callback causing target disposal or a new gesture; scene-exit re-entry; exactly-once invocation and sound; no denial cue on success; retained unsold offers/owned rack items; source return animation cancellation; keyboard/touch and real hit tests. Unit/protocol evidence alone does not prove shop browser behavior: adoption needs representative interaction evidence. No runtime code or visual acceptance is supplied by this document.

## Opaque carried-item protocol and rack adoption (#1433)

The partially delivered #1204 hand path does not complete rack adoption. Source audit at `9841e391`: `src/drag-drop.ts:DropTarget` and `DragDropManager.hitTest` require `RenderedBlock[]`; `src/table-input.ts:rackSource` carries `PassiveBlock` and performs reorder/use/sale separately. A rack item cannot enter the shared target protocol without either lying about that type or adding a source-kind branch. Preserve the delivered hand settlement and its existing owner; extend the common protocol rather than duplicating a rack-only target registry or silently excluding rack from Continue.

A gesture publishes a **carry descriptor**: opaque item handles, current visual/hit geometry supplied by the source, its one-shot source-settlement handle, and registered operation dispatch for the capabilities the source actually brings. A target's configured handler requests its required operation/payload through that dispatch; unsupported operations return the registered refusal/unavailable result. Generic collision detection and outcome dispatch use the descriptor uniformly, never inspect the item type, source name, trait-presence flag or a table of owner identities. Rendering pointers are optional operation payloads, not a required RenderedBlock cast for every carried object.

Existing card-only target handlers can use a registered card-payload adapter; the card source owns that payload and its admissibility. Rack ownership supplies its own existing reorder/use/sale operations and settlement through the same carry protocol. Those behaviors remain source/target rules, not decisions in the input manager. The return-action target needs only bounds, live registration and the settlement capability; it must not demand card-specific payload merely to return an owned passive. Do not convert rack reordering into a sale, purchase or discard as a side effect of sharing descriptors.

At release, retain the registered outcome handler and synchronous source acknowledgement described above. Rack return validates the captured item/group, restores its owned rack presentation and clears active carry before reporting success. Then recheck live target/action availability and invoke once. Cancel/lost capture/blur/source removal/scene exit returns without navigation. Stale descriptors/continuations cannot affect a later drag. Input source owns hover cleanup, preview restoration, floating visual disposal and authoritative command dispatch; presentation animation completion never authorizes the action.

Deliver one focused shared-descriptor/target-dispatch adoption, preserving current hand and offer compatibility, then complete rack source settlement/Continue adoption if that remaining boundary needs a separate PR. The implementer taking it has final workable delivery boundaries. Keep #1204's delivery membership open until its rack requirement is actually supplied; do not close it merely because the hand PR merged. Existing native blockers remain meaningful.

Verify hand, offer and installed-rack carries through shared hit/hover/release; normal card placement, buy/sell/reorder/use behavior unchanged; Continue returns each admitted source before one invocation; invalid operation refusal, stale/cancel/disposal paths and re-entrant navigation; keyboard/touch and actual hit regions. No casts concealing a missing capability, new generic identity branches or parallel manager. Source/protocol tests must be supplemented by a real shop rack-to-Continue browser check.
