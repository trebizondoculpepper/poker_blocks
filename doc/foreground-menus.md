# Foreground title and pause menus (#627)

Owner-approved target for #628 and #530; Settings deliberately keeps its readable panel and real text controls. Source evidence: `menus.ts`, `block-menu/block-menus.ts` and `block-menu/cube-stage.ts` already separate dialog content/accessible actions from a three.js menu-cube stage; `menus.ts`/scene traits own showing the host. Inspect their current mounted style classes at implementation intake rather than removing the application's renderer canvas. The existing [input ownership](game-architecture.md#input-284-epic-271) and [menu scenes](game-architecture.md#menus-as-scenes-87) contracts remain authoritative.

## Composition and layer ownership

A reusable menu host accepts explicit presentation configuration: `panel: none|readable`, foreground placement/layout, accessible action list and covered-scene activity capability. These are registered style/layout/scene-stack behaviors, not branches on a title/pause/settings identity. Title and pause definitions compose the **panel-free foreground** configuration. Remove their legacy opaque/translucent menu rectangle/backdrop and any equivalent CSS pseudo-element behind choices; do not replace it with a different full-screen scrim. Their full-screen pointer-routing surface may remain transparent for input isolation.

The existing 3D attract scene remains visible and **running** behind the title menu. The paused play scene remains visible but **frozen** behind pause choices; freezing is the covered scene's configured simulation/presentation pause behavior, not hiding its framebuffer or delaying model commands from an animation. The foreground menu's own spring/hover/tap feedback continues. Never stop the shared clock for the whole app merely to freeze the covered playfield. The scene manager dispatches configured suspend/resume capabilities to the covered scene, preserving exact board/camera pose and restoring it on Resume.

Keep the block title and existing non-menu information such as version/footer/warnings unless a separate decision removes them. Cubes remain foreground at readable size with no rectangular panel behind them. Pause uses one horizontal row: **Resume, Settings, Quit to title**, in that order; narrow viewports wrap through the shared layout engine without clipping or overlap, keeping logical keyboard order. Initial target-centred placement and spacing are reversible layout defaults; inspect three-dimensional intersections/occlusion in portrait and landscape.

## Title cube size: the Dev13 audition reference

The owner's corrected reference is the menu-block audition room at `?mode=dev13`: main/title menu cubes should have approximately the same apparent CSS-pixel edge size at matched viewport dimensions and device scale. This supersedes the earlier 1.1× title-letter rule wherever they differ. Do not compare a whole word, the complete audition grid or title lettering. Hover/dance transforms are not the neutral sizing reference. Pause/Settings receive no new relative-size requirement from this decision.

Source audit: `tools/word-cube-room.ts:gridPositions` uses seven items, four columns, two rows and center spacing 1.7. `block-menu/cube-stage.ts:fit` uses margin 1.8, the shared attractFieldOfView, and camera distance max(height/(2tan), width/(2tan×aspect))+1. The audition stage uses a full-viewport grid with auto header/footer (`tools/word-cube-room.css`), while production dialogs have different hosts. Independent fit cameras can scale a two-choice production menu much larger even with identical world-space cubes. Copying mesh scale or importing a dev room into production is not a solution.

Use a shared configured **reference sizing profile** and generic projection/layout helper, composed into both the reference and production menu hosts. Profile data records a fixed four-column/two-row frame (bounds width 6.9, height 3.5), spacing 1.7, fit padding 1, the existing FOV, and the reference canvas rectangle policy. As an initial reversible source-derived authoring approximation, use full viewport width and viewport height minus 82 CSS pixels for the header/footer; this is not a browser measurement. The actual audition host can publish its measured canvas rectangle through the same metric provider, and responsive refinements belong in the shared viewport-layout configuration, not a table keyed by room ID.

The helper projects a canonical unit cube front horizontal edge at the neutral reference transform/camera into CSS pixels. A unit cube has its front plane at z=0.5; with the above fit distance D, the projected edge is referenceCanvasHeight/(2tan(FOV/2)×(D−0.5)). Production title layout consumes that resolved target edge with ratio 1.0 and must not independently refit it away. Definition configuration supplies the reference profile; generic services never ask whether they are rendering title or dev13. Extract shared source constants/configuration rather than copying two diverging formulas.

Verify with side-by-side neutral screenshots at the same viewport/device scale, recording actual reference/menu edge pixels at desktop landscape and mobile portrait plus resize. Initial approximate-match tolerance is 10% as an authoring aid, not a user-approved fixed numeric size. Where the 82px reference approximation misses wrapped header/footer behavior, refine the shared rectangle profile from measured reference bounds; do not return to the superseded letter ratio or ask the owner to choose the size again. Keep labels, spacing and focus readable without expanding production cubes simply because there are fewer choices. A narrow-screen clamp is explicit responsive configuration, checked against the same reference rather than silently cropping controls.

This design records source evidence and a reproducible comparison method, not a claim that the browser comparison has been performed. Implementers supply screenshots/metrics. Confirmation choices can share the configured profile while retaining their readable warnings and configured Cancel focus.

## Settings and navigation

Settings remains text with real sliders/toggles on its readable panel. Its Back action may use a menu cube under #530, but this does not convert sliders into cubes or remove Settings' panel. Returning from Settings to pause leaves the underlying playfield frozen; returning to title resumes the attract scene. Existing save/confirm/quit and Escape semantics remain unchanged. A reusable scene-stack activity configuration owns these differences; generic menu code receives resolved host behavior.

## Input, inspection and cleanup

The foreground menu owns its input layer while shown. Cubes compose inspectable, available/unavailable explanations, standard spring motion and keyboard/touch actions through the shared block-menu controller. Accessible semantic buttons remain mapped to the same registered action; hiding visible text menus does not remove accessibility. A transparent backdrop must still prevent pointer/keyboard fall-through to covered gameplay. Gesture adapters route to owners, never inspect scene identity. The configured initial action has precedence: new-game confirmation retains `cancelNewGame` / Cancel, preserving the protection against repeated Enter overwriting a save. Only when no valid configured focus exists does focus fall back to the first enabled action. Focus travels in logical order and returns appropriately when closing the menu.

Scene exit disposes the foreground stage, observers, listeners and owned geometry/materials, not the covered scene's renderer/shared resources. Suspended scope cancellation/resume uses the existing scene contract; stale menu callbacks cannot navigate a later scene. Existing UI/navigation sounds retain their owners, once per action. Reduced motion follows the spring/menu effect configuration while preserving readable controls.

Acceptance: title running scene visible behind panel-free cubes; pause exact frozen board visible with active menu feedback; Settings panel and working controls preserved; Resume/Settings/Quit row, keyboard/touch and inspectable descriptions; no input fall-through; confirmation/save behavior; resize/portrait; repeated enter/exit with no leaks. Provide before/after screenshots and a short pause/resume clip at the tested revision. This is a documentation decision, not a claim the background removal already shipped.
