# Gameplay lifecycle, events and context (#611)

**Target contract.** This document defines the architecture to implement in #612–#614. It does not claim the full lifecycle is wired today. Evidence, alternatives and verification limits are in [the source audit and geometry probe](research/gameplay-lifecycle-opportunities.md) (#615). Existing `EventRuleRegistry`, `commitCommands`, `PassiveEventQueue`, reaction and trigger registries are the foundations to extend, not replace with another gameplay bus. The visual scheduler is a separate presentation mechanism.

## Ownership and composition

The gameplay coordinator owns validated action resolution and phase boundaries. The dealer supplies validation, allowances and outcome rules; the ordered deck, hand and field retain their contents ownership. A **model controller trait** subscribes to phases and coordinates registered rule/command handlers. It does not mutate state directly. A **presentation controller trait** consumes captured outcomes and requests services; it cannot issue gameplay commands. Services know neither game identities nor game policy.

`materialEffectsController` is one model controller trait composed onto the playfield. Its configuration attaches registered phase handlers for placement, pre-score and post-score behavior. Block definitions bring registered reactions, triggers and settings; the controller delegates to them uniformly. It does not branch on material names, inspect traits as flags, or contain a table of material identities. Without this composition the field installs no material-effect subscriptions; the gameplay coordinator has no material-effects toggle or conditional path. Other traits can subscribe to the same lifecycle independently.

Attachment registers subscriptions and returns disposal handles. Detachment removes them once, including scene/run replacement. Rendering a second view does not attach another model controller. Model attachment follows the authoritative run/field lifetime; visual scene exit alone must not disable model rules. Save restoration reconstructs subscriptions from definitions and saved state, without replaying placement, stage-start rewards, opening or RNG draws.

## Numbered stage lifecycle

Each round contains **stage one, stage two and stage three**, represented in lifecycle context by `stage.ordinal` (1, 2 or 3) and `stage.round` (positive round number), with a stable stage-instance ID for correlation. “Boss” is a gameplay label for stage three, not a lifecycle category. Dealer selection and display labels live on the stage definition and may vary independently of its ordinal. Generic lifecycle code does not test a dealer or label to discover the stage.

Every stage publishes `stage.started` after setup/deal, and exactly one `stage.won` or `stage.lost` after model scoring/material actions and outcome settlement. Definitions subscribe through registered conditions: an ordinal-2 condition on `stage.started` applies to stage two in every round, without firing at stage one/three; adding a configured round condition narrows it further. The same filtering works independently for won and lost. Event vocabulary does not multiply into a distinct event name for every round/stage combination. Registries dispatch event/condition handlers; the coordinator contains no ordinal-specific policy branch.

Captured ordinal/round context cannot change when a later stage starts or delayed visuals play. Restore/Continue does not replay start/win/loss as a fresh stage. A response to stage three being won supplies the configured Present reward, rather than hard-coding a boss test. Stage one/two/three are canonical design terms. Existing serialized `kind` values `stage-1`, `stage-2`, `boss` are legacy compatibility handles; migration maps stored progression definitions to ordinals at the parsing/configuration boundary, not by scattering identity comparisons through gameplay. Do not invalidate existing saves or rename storage keys without the explicit compatibility work.

## Event and command contract

Definitions contain serializable registered handler references and configuration, not closures. The shared registry validates event, condition, query and command references at composition time. An event envelope carries:

- stable event type and unique event ID;
- action ID, sequence number and parent event ID (where caused by another event), plus run/stage/round context;
- phase and scope, including batch ID and ordered subject IDs where applicable;
- immutable captured payload and an explicit read-only model snapshot/version;
- registered working-value capability only during a mutable phase; completed facts have no such capability.

IDs correlate facts and locate instances; they never choose behavior. Each event schema states its granularity and fields. A batch is emitted once per successful action; per-block facts are emitted once per actual transition in that batch. Subscribing to both deliberately receives both: the runner must not silently deduplicate legitimate events. Duplicate action submission is rejected at the action boundary; reward/payment deduplication remains authoritative and saveable.

Handlers receive the captured event and query interface and return ordered typed command descriptions. Command handlers own permitted mutations and emit resulting facts. A command declares which phase/target capability permits it. Unknown registrations, invalid targets and attempts to rewrite a finalized score are explicit errors, never ignored commands. Source snapshots remain immutable even as subsequent commands advance the working state; a handler that needs current working state receives an explicitly versioned view, not an alias hidden inside an old event.

Arrays, nested block data and hidden payloads require immutable copies or immutable structural sharing. `Object.freeze` on the outer envelope alone is insufficient. Internal traversal sets and transaction machinery are not exposed as event data. Capture only needed context: immutable does not mean deep-copy the entire run for each fact.

## Resolution order for a play

The following is synchronous **model** order. It does not wait for an animation, sound, timeout or visual queue drain.

1. **Validate and commit placement.** Validate the whole requested group against dealer/drop rules. An invalid request consumes nothing and emits no successful placement/scoring events; it may request rejection feedback. A successful action stages the ordered hand-to-field transfers and consumes its play allowance once. `play.placed` is the once-per-action placement batch; `block.placed` reports each placed instance in placement order, initially including any wrapper. These are committed-placement hooks, not permission to bypass validation. There is no generic mutable pre-placement callback in this first contract; future legality modifiers require documented validation capabilities.
2. **Resolve opening/replacement.** Placement opening handlers adopt stored contents through registered commands. Each successful opening emits `block.opened` with wrapper and revealed snapshots and the replacement identity relationship. Resolve all placed wrappers in placement order before material phases. Opening is not destruction, discard, or a second placement action. Rules needing the revealed material use the subsequent phase's resolved field, not an extra synthetic `block.placed` event. Present contents were fixed when the opaque container was created (a stage-three completion reward; see [Presents](presents.md)); opening performs no new roll.
3. **Pre-score material phase.** Emit `play.beforeScore` once with resolved placements and field. The composed material controller runs registered placement/pre-score steps in declared order: explicitly placement-timed interactions (including the approved air/flame upgrade), then countdown deductions. A countdown reaching zero records a pending trigger for the post-score phase; it does not detonate before scoring. Drain follow-up gameplay facts/commands for each step before advancing. Other reactions remain post-score unless an agreed rule explicitly assigns them earlier timing.
4. **Score.** Discover maximal X/Y/Z lines from the resulting field. Keep line finding, poker evaluation and trial/candidate valuation pure. The committed scoring coordinator invokes registered working-score phases (`score.beforeBlockValue`, `score.lineMultiply`, `score.linePower`, `score.beforeLineFinalized`, `score.afterLineClamp`) at their documented points. Existing contributor eligibility and score arithmetic remain unchanged. Emit `score.lineFinalized` once per committed line result, then `score.allLinesFinalized`. `score.beforeTotalApplied` may change the working aggregate delta, never a finalized line. Apply it once and emit `score.totalApplied`. A trial evaluation must never dispatch reward commands or consume RNG/uses.
5. **Post-score material phase.** Emit `play.afterScore` once with finalized results. The initial configured step order is post-score reactions, then pending countdown detonations, draining follow-ups between steps. Pending detonations retain countdown-discovery order; a source removed by an earlier command is no longer a valid target and cannot detonate twice. Use a fresh entry snapshot for this configured reaction step: pre-score changes are visible here in the same play. Select the first matching applicable reaction per block once in this step; do not automatically rescan to a fixed point. The old blanket one-step-per-play rule is superseded by [phased material consequences](material-phases.md). Detonations use registered trigger behavior, resistance and removal/transfer commands. They cannot rescore or rewrite this play's finalized lines. Registered phase step order is configuration, validated for completeness and determinism, not an identity switch in the coordinator.
6. **Settle the action and outcome.** After every model phase and its follow-up commands completes, evaluate dealer outcome. `stage.outcomeProposed` is a deliberate mutable outcome opportunity; only explicitly registered outcome commands may affect it, followed by re-evaluation. Emit exactly one final `stage.won` or `stage.lost` when decided, then `play.completed` with the complete action summary. This is the target timing for `play.completed`, later than the legacy post-dealer-score event. Finalized outcomes cannot be undone by a presentation or final-outcome listener. Preserve once-only reward ledger/payment and existing stage/shop progression rules.

All step sequences are registry-dispatched configuration. The coordinator owns generic boundaries and barriers, not material-specific policy. Existing events/consumers must migrate explicitly to this timing; do not dual-emit legacy and target events to the same listener. Non-play actions use their own validated command paths and emit only their relevant facts; discarding or destroying outside a play does not silently consume a play or invoke scoring.

## Delivery order, cascades and failure

At event delivery, snapshot eligible subscriptions and their ordering. Listener configuration declares its owner scope and order: rack listeners use captured left-to-right rack order; field listeners use stable placement/ownership order (not render order); phase steps use their declared sequence. Cross-scope order is declared by the phase composition, never by a material/item ID or accidental Map iteration. Each listener's commands apply in returned order before the next listener runs; subsequent listeners can see the updated, explicitly versioned working state. Subscription changes affect the next delivered event, not the current listener snapshot. Mere existence in a zone does not subscribe a block: its composed capability registers the relevant owner scope.

New ordinary follow-up events enter the shared gameplay FIFO after the current event's listeners finish. Drain to the current phase barrier before moving to the next phase. Existing trigger-response traversal remains explicitly depth-first inside its registered trigger command, with visited protection; its outward facts join the shared FIFO. Do not change trigger semantics by treating every internal recursive step as a new independent top-level action.

One action-wide resolution budget covers ordinary events, handler invocations, commands and nested trigger steps; nested drains do not replenish it. Initial limits are 128 delivered ordinary events (preserving the existing queue default) and 4,096 combined handler/command/trigger operations, configurable as run resolution limits and captured in diagnostics. No wall-clock timeout determines a gameplay result. An overflow reports the action/event ancestry, phase and registration responsible; it never truncates a successful result or applies a visual scheduler's drop/coalesce policy to model commands.

Stage action mutations, ownership changes, rewards, use consumption and RNG cursor in a transaction. Publish authoritative state, facts and presentation records only after successful resolution. An error rolls back that action's state and RNG together and publishes no partial gameplay success or reward; diagnostic feedback is allowed. This is a target guarantee, not a claim that legacy mutating runners are transactional. External sound/render/service calls are forbidden during this transaction. Restoration rebuilds state and subscriptions without re-running an action; published visual callbacks are not saved as gameplay instructions.

## Lifecycle vocabulary and extension

The initial migration must expose placed/opened/discarded/destroyed facts and the play phases above. Existing stage/shop/reward events keep their established guarantees. Further families below are extension points, not a requirement to implement every event before material integration ships. Adding a family requires a schema, mutation owner, granularity, ordering, capabilities and tests in this contract; it never requires an item-specific branch.

| Family                   | Initial fact/phase vocabulary and boundary                                                                                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Placement/opening        | `play.placed` batch, `block.placed`, `block.opened`; opening includes stored replacement, not destruction                                                                                             |
| Discard                  | `discard.completed` once per action plus `block.discarded` per actual transfer; no duplicate allowance consumption                                                                                    |
| Removal                  | `block.destroyed` only permanent authorized destruction for the run; `block.removed` reports the lower-level removal and reason; an explicit destroy command emits both deliberately correlated facts |
| Resistance/trigger       | Existing `block.triggered`, `block.resisted`, `bonus.transferred`; request rejection/resistance is not a successful destruction                                                                       |
| Scoring                  | Working phases and immutable final line/all-lines/total facts above; candidate evaluation emits none                                                                                                  |
| Progression              | `stage.started`, `stage.outcomeProposed`, `stage.won`, `stage.lost`, `reward.finalized`, `shop.entered`, `shop.left`; final rewards paid once including after Continue                                |
| Future ownership/economy | Draw, shuffle, zone transfer, inventory change, purchase, sale, shop stocking, reorder: emitted by their authoritative owners, with ordered before/after facts and actual amounts                     |
| Future state/boundaries  | Material change, modifier acquisition/reset/transfer, item use/exhaustion, round/run boundaries and restoration: distinguish state reset, retention expiry and explicit removal                       |

An unopened Present composes ordinary discard behavior. Destruction removes a card from all run ownership so it cannot be dealt again; discard, stage collection, retention expiry, reset and wrapping replacement are distinct transitions. A Nothingifier's deliberate removal need not masquerade as an explosion. Permission/resistance is handled by the requested command's registered cause capability; presentation cannot grant destruction. Generic code does not branch on a cause string.

Stage context includes round and configured stage rules. Identifiers remain lookup handles; a trait's registered condition evaluates its configured rule. On a win, reward handlers produce the existing ledger, paid once from the documented balance snapshot; final outcomes and payments are not replayed by Continue. Do not emit a fake new `stage.started` during hydration through a dummy constructor.

## Registered context queries

A lifecycle fact and a derived context query are separate capabilities. Use registered pure providers, requested by trait rule configuration, over an explicit immutable snapshot/version and scope. The query interface returns a value or a typed `unavailable` result; it cannot mutate, consume RNG or emit gameplay events. The same snapshot, scope and query configuration returns the same result. Cache within that immutable version; occupancy-dependent caches cannot survive occupancy changes. Never close over a later live `GameRun.state` behind an earlier event.

The first provider slice may expose occupied count, inclusive integer bounding box/extents/volume/density, and six-face neighbors. Empty-field bounds are absent and density is zero by definition; each nonempty extent is max − min + 1. Validate coordinate arithmetic and safe volume representation. Density is occupied cells divided by that volume, so a filled line and a filled cube both have density 1; this is not an implicit preference for cube-like shapes. Scope explicitly identifies whole field or selected cells; no hidden camera/render bounding box is authoritative.

Providers advertise cost and deterministic input-size limits. Reuse the snapshot's cell index and computed scoring context; do not rerun the best-hand search for an incidental metric. Bounds scans are O(n); six-neighbor lookup is constant after index construction. Connectivity and especially exterior void flood fill are separate opt-in providers. The research's bounded probe is not a production topology algorithm. An unavailable query is never a numeric zero or an automatic missing bonus: a gameplay rule requiring it must declare a registered deterministic fallback or reject the action transaction with a diagnostic. Budget decisions depend on inputs/configuration, never machine speed. Ordinary placement requests no expensive topology work without a subscriber.

No dense/sparse/void reward, topology definition or payout is approved by this contract. Those remain #616. Public inspection queries cannot expose concealed Present contents; authoritative opening may access its stored payload through a narrower capability. Event/public/debug views must respect that visibility distinction.

## Presentation and verification

Successful model resolution exports immutable ordered presentation records with action correlation, captured subjects and pre-score/scoring/post-score dependencies. The visual queue may schedule follow-ups, including staggered item activation, but never re-evaluates game rules against newer state. Reveal delay (five game-time units by default) belongs to presentation: wrapped placement → reveal → pre-score effects → scoring → post-score effects. The player may make another valid move while old feedback plays. Stage completion presentation waits for the completed scoring/material sequence for that action; model outcome/rewards need not wait. Scope cleanup may cancel visuals, not roll back committed gameplay. The scheduler, its clock, units, scopes and result-screen gating are defined in "Visual-event scheduler and game-time units" in [game-architecture.md](game-architecture.md) (#541).

Implementation acceptance is sliced: #612 supplies lifecycle/transaction boundaries and facts; #613 installs configured material controller subscriptions and phase handlers; #614 replaces direct gameplay material dispatch and integrates model/presentation ordering. Reuse existing ownership, stored Present replacement, reset and visual scheduler missions rather than duplicate them. A separate context-provider slice can implement the first cheap queries after this documentation merges.

Tests must cover ordered multi-placement/opening before material phases; countdown before score and detonation after; no controller composition versus configured composition; rack/field listener snapshots; commands and nested cascades sharing bounds; atomic state/RNG rollback; one-time restore/rewards; discarded versus destroyed versus replaced identities; immutable captured context under a later move; and input remaining available during delayed visuals. Test cheap queries independently, including empty field, thin shapes and unavailable results. Passing existing registry tests alone does not verify this lifecycle.
