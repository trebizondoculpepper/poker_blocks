# Resolved gameplay-block lifecycle declarations

Documentation prerequisite #915 for #916 resolver and #917 definition migration, split from #504. This makes the existing [clone/reset contract](clone-reset.md) concrete; it does not implement boundary execution or change ownership by inference. Boundary execution remains #505/#506 and the ordered-card lifecycle integration.

## Declaration and resolution

Every gameplay card, active and rack-item definition admitted to the run's model resolves one retention value (stage, round or run) and one reset facet (resettable with recipe/boundary, or nonResettable with reason). A declared single parent supplies plain defaults; a local declaration replaces the complete retention or reset value. Resolve once at registry validation through shared lookups, rejecting missing/unknown parents, cycles, unresolved fields, contradictory facet members, invalid boundaries/targets and unknown reset handlers. No parent is guessed from material names, instance IDs or scene membership.

Declaration data belongs to its definition or its registered definition-producing factory; the table below is an authoring matrix, NOT a runtime identity-keyed policy map. Stateful appearances such as cooked meat or heated Water can share one material definition and inherit its behavior without needing a new identity per visual state. Future derived definitions explicitly select their parent and any complete overrides. A reset recipe uses registered component-state handlers, never reflection over arbitrary fields.

Scene/UI render nodes, menu action visuals and emitted particles do not become run-inventory entities merely because they use cube geometry. Their scene/resource disposal remains separate. Any actual gameplay instance represented by such a visual still needs the gameplay lifecycle declaration; render identity cannot select exemption or behavior.

The ordinary material row includes materials that are not shop stock; catalogue availability does not decide lifecycle. Cloud's stage retention applies even if a dev setup made it deck-owned. A generated temporary Cloud also has stage retention and field ownership, so it does not join the deck. Other temporary generated materials require their own explicit derived/factory declaration rather than inheriting run retention by accident. Ownership chooses where a surviving instance returns; retention determines whether it survives.

Appearance-only prototypes inherit the intended gameplay parent's values through their own declared configuration. Render-only gallery objects do not participate in run cleanup. Migration #917 must audit every installed material/active/rack definition and generated factory, including experimental definitions admitted by the current mode, with no hidden registry default or material-kind switch. Unsupported new definitions fail composition rather than silently gaining run retention.

## Recipe composition and timing

Use existing resettable/nonResettable registry behavior. Meat uses the registered doneness handler; Gelato uses material with configured target Custard; countdown state uses the countdown handler. These are operation names on the authored recipe, not generic material branches. A boundary reset preserves instance identity, rank/suit and owner unless an independently configured command changes them. No reset draws RNG or rerolls a stored payload.

Because a local reset override is COMPLETE, an authored combination such as a cooking card with a countdown must explicitly preserve both intended handlers in its ordered recipe. The definition/factory can use a registered recipe-composition operation to construct that value; the resolver must not scan trait flags or concatenate conflicting declarations implicitly. Test combined recipes so adding one capability cannot accidentally erase another's reset behavior. A recipe is scheduled at its configured boundary, not by reading the material name.

Settle/pay outgoing rewards first, expire retention, reset survivors, clear the independently matching modifier-lifetime registers, transfer survivors to their owners and shuffle according to ordered-card-ownership.md. An expired card is not reset afterward and expiry is not destruction: no bomb transfer or destruction audiovisual effect is implied. Stage/round/run acquired bonus registers clear only at their own boundaries; a material recipe must not erase permanent modifiers or conflate intrinsic material state with an acquired register.

Gelato persists across stages and reverts after a round. Meat's doneness is available to Le Chef's outgoing reward calculation before stage reset. Water's intrinsic heated/boiled state has no new automatic cooling rule. Unopened wrappers keep creation-fixed contents; normal Present acquisition already selects eligible ordinary payloads, and this migration must not silently rewrite a payload's lifecycle to make a conflicting future factory work. Such a new acquisition/lifetime conflict returns to documented design.

## Persistence and compatibility

This resolver/migration declares policy on definitions; it does not serialize functions, duplicate lifecycle data in every save or run boundary effects on hydration. Existing supported records resolve their current definitions and retain current material/state/modifiers/uses, including fixed payload descriptors. No reward, reset, retention expiry, shuffle or sound replays on Continue. Lookup/restoration remains separate from new catalogue eligibility.

Use existing state and rack/component codecs. No save-version change or new lifecycle override field is authorized solely to implement #916/#917. If an existing saved instance needs a genuinely new serialized override that cannot be reconstructed from its valid definition/component data, document that exact codec/version/compatibility change first. Do not drop unknown state or weaken exhaustive ownership validation. Retired definitions needed by existing valid instances remain resolvable; retirement does not delete owned objects.
