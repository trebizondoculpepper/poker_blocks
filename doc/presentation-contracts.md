## Acquired bonus artwork and inspection (#432, #751)

`acquiredBonusDisplay` is a presentation capability composed into card artwork. A pure modifier query combines active registers using the model's existing arithmetic (sum adds, product multipliers, sum exponent increases above one). It returns the full breakdown and compact descriptor. Priority is exponent, multiplier, additive; neutral values are `1`, `1`, `0`. Base material values are separate. The renderer formats the descriptor; it does not recompute scoring, select lifetimes, or inspect material identity.

On each printed face rank and suit occupy **top-left**, compact acquired bonus **bottom-right**, in face-artwork coordinates, with a consistent inset. Start with 8% inset and bonus glyph height 15% of face width, configurable for audition. The label is `+2`, `×6`, or `^1.3`; lower-priority modifiers remain active but hidden on the face. Neutral acquired modifiers produce no label. Display numbers with at most three fractional digits, trimming trailing zeros; never round persisted/scoring values. If a non-neutral value would round to neutral, use enough significant digits to distinguish it. Inspection retains a non-lossy numeric description.

The existing `inspectable` capability composes a live model description provider with the ordinary card/material description. Show a compact **Base** section when available, then non-neutral **Stage**, **Round**, **Run** rows (localized display names supplied by registered lifetime metadata) and **Combined acquired** add/multiply/exponent values. Include expiry text from each registered lifetime. This prevents an invisible additive bonus disappearing behind the displayed power. An unmodified card says no acquired bonuses; it does not invent a zero-valued benefit. Providers are registry-dispatched; inspector hosts do not branch on trait presence or material.

Refresh from authoritative card snapshots on register/material change and lifecycle reset. Artwork invalidation is scoped to changed cards and cached by immutable artwork inputs; do not regenerate textures every frame. Inspection updates while visible. Save restoration rebuilds descriptions without activation/reward replay. Dispose owned artwork copies on replacement while retaining shared textures. Verify mixed registers, neutral cases, reset, material change, Continue and rotated faces; screenshot both label and inspection. Rank/suit rules and hand evaluation do not change.

## Committed transition fact and independent responses (#479, #539)

A successful registered material-change command emits `block.materialChanged` **after commit** with the immutable lifecycle envelope (event/action IDs, sequence, source, phase), stable block ID, before/after card and appearance-description snapshots, and location/pose reference. Pose is a live presentation mount reference by ID, never a mutable mesh in model data. The authoritative material-change path, used by transmogrifier and reaction commands, owns emission. It emits nothing for rejection, missing target, same material, preview or restore. Existing direct paths migrate into this command seam; do not infer changes by diffing frames. This is an added target event, not a claim an identical event already exists.

`materialTransitionController` and `materialChangeSoundController` are independent composed presentation controller traits subscribed to this committed fact. Each queues its own registered presentation request with stable event-derived deduplication key. The visual request occupies its captured pre-score or post-score presentation phase; audio is scheduled at transition start in that same phase, without depending on dissolve completion. The model is already committed, input remains available, and completion cannot mutate state. Use the shared visual scheduler foundation; when it is not built, record that dependency instead of using blocking timers or a second queue. Play-phase presentation order follows `game-events.md`; non-play item use has its own action sequence.

The visual definition supplies `materialTransition` with a registered handler reference and serializable settings. Resolution precedence: explicit configured action response, composed scene transition default, then default `perlinDissolve`. No per-material lookup table; a target definition may supply an explicit alternative. Default duration is 0.5 seconds, noise scale eight blobs across the block, with bounded edge glow; reduced motion uses a short crossfade (0.12 seconds). Export these as tunable presentation settings, not scoring delay.

Build old/new appearances from captured definitions under one following mount at the same position, rotation and scale, initially old visible/new masked. Use one normalized block-local noise domain, one seed and clock for complementary masks; differently sized bounding boxes must not create holes. Reuse `createMaterialise` mechanics, adapting a shared mask input where necessary. Outlines/artwork belong to their respective appearance and obey the same visibility. Preserve contained updates and registered optical passes; do not add an opaque cover or disable all depth tests to hide sorting defects. Transparent/special shader adapters declare support; validate required adapters at build time. Missing support is explicit and needs a focused follow-up, never an invisible new representation.

A second committed change cancels the obsolete transition at the last displayed pose and immediately uses the previous committed target as its old snapshot; no growing stack or replay of earlier sounds. Leaving the zone/removal/exit cancels owned work, restores any host material references and frees only owned clones/appearances. Queue action scopes prevent late completions replacing newer visuals. Shared passes/resources remain renderer-owned. Test rejection/same-material silence, rapid changes, rotation/flight, containment, cancellation, restore and reduced motion.

Sound selection is on the **target material definition**: `transitionSound` is a registered SFX ID, optionally inherited through normal definition composition. Default stand-in is that definition's existing attach sound, copied into its resolved configuration rather than chosen through a dispatcher identity check. Register a distinct target transition ID with placeholder metadata where bespoke audio is absent. Existing action audio stays if it describes a different action; remove duplicate material-change playback from old callbacks. One successful committed change plays at most once per sound-response subscription/event. No remote generation or credentials at runtime; use `sound_design.md` provider dispatch.

## Resolved activation results (#483)

Extend the existing committed activation record with stable activation/action IDs, captured source identity/description reference, phase, optional line and target IDs, captured rack/field order, and ordered **resolved outcomes**. A registered effect handler reports `{operation, operand, before, after, unit, scope, targets}` for each applied operation. Operations are registered names, units identify score/coins/etc.; values and scope are typed and validated by the handler. This is a schema contract; exact TypeScript names can follow repository conventions. Numeric arithmetic remains at the effect's model execution site. Targets and values are snapshots, not live object pointers.

Record only selected/committed activations. Candidate scoring may produce speculative records locally but cannot publish them, consume additional RNG or issue commands. Commit command-produced outcomes once alongside the containing transaction; rollback discards all records and restores RNG/state under the lifecycle contract. Discard and other non-scoring activations use the same envelope with their own action/phase and no fabricated line ID. Repeated triggers receive distinct activation IDs and occurrence order; visual stagger schedules these immutable records without rerunning rules.

A die reports its actual resolved operand (for example `add 6`), not a recipe that rolls again. Crossroads reports the effective result of its already evaluated geometry/rule, not a new field query after later moves. Descriptor traits (#484) format these outcomes, while pulse traits (#485) choose their own presentation. Hosts forward the same activation ID to both; label duration comes from the configured effect. Empty/no-op outcomes are explicit and must not be presented as an invented bonus. Tests compare scoring/discard arithmetic before/after payload addition and prove no extra RNG/effect application. This ticket supplies data, not the row-score popup or label renderer.

## Laser target-guide controller (#500, #501, #502)

Compose `dropTargetGuide` on the shop scene, configured with registered target-area providers, eligibility source, guide shape/style and **preferred source guidance**. Rack items/passives guide to the rack; playable cards guide to BUY. This preference is declared on the drag-source definition/provider and is independent of all targets that can actually accept it. A passive may still be bought through BUY. No generic source-kind switch is permitted.

The controller mounts one pointer-transparent overlay canvas owned by the scene's HUD overlay layer, above target backgrounds and below tooltips. It uses an orthographic camera in CSS-pixel coordinates. Provider rectangles come from the real drop targets' `getBoundingClientRect`; convert viewport rects into overlay-local CSS coordinates, with device pixel ratio applied once to buffer sizing. Read live rectangles on drag changes, scroll, resize and observed target layout changes. Canvas clips to its host; it neither captures pointer events nor defines acceptance hit tests.

Subscribe through registered drag source/target lifecycle handlers: began/changed/ended/cancelled, lost capture and source/target disposal. Use the existing live purchase verdict provider (`ShopView.dragVerdict`) for price/capacity and the actual target eligibility contract, never recompute shop rules in the overlay. Eligible preferred target draws the laser rectangle; rejected intended target draws a red diagonal X via `createDropGuide`/registered shapes. Nonpreferred areas remain unhighlighted, even if valid. A rejected drop still follows the independent 0.5-second fly-back contract (#482).

Hide immediately when drag ends/cancels or the source disappears. Dispose subscriptions, observers, renderer resources and geometry on exit; stale callbacks cannot affect a new shop. Reduced motion freezes the laser's noise drift while preserving shape/colour and the ordinary accessible rejection explanation. The overlay adds no gameplay or sound event; accepted/rejected actions use their existing sound owners. Verify scroll/resize/DPR, rack full/funds changes during drag, both purchase paths, cancellation and touch.

## Smoke/dust audition composition (#466)

Use **experimental appearance definitions**, not a mode-keyed material override map and not a production rollout. Each experimental definition is a normal derived material definition retaining its parent's gameplay traits but adding the selected `smoke`/`dust` appearance effect configuration. Register these with the experimental catalog; include explicit description that they are audition looks. The mode's run-setup deck recipe receives a weighted list of these definitions (fire-like and earth-like entries), with equal weights initially and no production save/deck mutation. Reference a registered setup step, extending the existing configured experimental-deck setup pattern if necessary; generic dealing reads weights uniformly.

Compose a `Dev`-prefixed audition trait and normal board gestures into the dev mode definition in `game-modes.ts`. The host renders the resolved card appearance without checking the mode. Definitions add effects through the existing `blockEffects` registry, using per-instance ownership and world-space particles. No global material registry mutation on entry, so other simultaneous views retain production appearances. Scene exit disposes particle pools and tool-owned objects; continuing a saved production run does not acquire experimental looks. Smoke remains continuous/world-up; dust uses configured rotation threshold and emission proportionality. Existing accurate smoke/dust parameters remain in the architecture. This choice resolves the missing mode-scoped composition question without introducing another generic override subsystem.

## Object browser manual rotation (#746)

A reusable `devPreviewRotation` controller owns preview pose. It mounts the existing use-gesture drag handler on the preview, not on property controls, and converts mouse/touch delta into camera-relative yaw/pitch quaternion updates. The first drag pauses automatic turntable motion **before** changing pose; on release keep the chosen orientation. No clamp that makes a face unreachable. Keep internal visual animation advancing independently of object rotation. A labelled **Auto rotate** control resumes turntable from the current pose; **Reset view** restores the documented three-quarter pose and manual mode. Use existing UI click sounds; drag uses the existing gesture action sound if one is already provided, without duplicating it.

Default sensitivity is 0.01 radians per CSS pixel, configurable. A cancelled gesture ends ownership without snapping. Touch-action is scoped to the preview, keyboard controls offer rotation/reset, and other controls/page scrolling outside the preview remain usable. Switching entries preserves the current viewing pose as a tool preference and disposes previous mounts; switching/exit cancels handlers. Do not use a room-identity branch in input adapters or overwrite the manual quaternion from `spin`.

## Material audition corrections (#742–#745)

**Water inclusions (#742).** Bubbles must be visible inside Hot and Boiling Water from the top and either side, including the usual three-face view. Preserve their different rise speeds. Reuse the existing pool/liquid-surface behavior. Extend the contained optical composition with a registered **interior contribution pass**: the optical contents handler owns integration of its volume's particle contribution before the final surface reflection/print, using the common boundary/depth data. Opaque fluid/shell depth must not hide all side-view particles, and particles must not overlay outside their vessel. Where the current transmission pass cannot include a contribution correctly, use an explicit renderer-owned offscreen interior layer and sampling adapter at that contents handler; do not turn every material transmissive or add per-object full-scene captures. Share compatible immutable resources/capture epochs, retain per-volume membership. Correct sorted layering/overlaps are verification requirements, not established facts from the source audit. This can reuse the gallery interior capability in the water prototype contract; #676 remains gallery work, not a substitute for correcting existing water definitions.

**Flame distinction (#743).** Same registered flame contents handler, two configurations. Start regular flame at the existing intensity and Aggressive Flame at 1.5 times its intensity, 1.15 times its density-envelope height (clamped within the common boundary), with a more prominent pale/yellow core; keep regular red/orange edge emphasis. These are audition defaults, not literal Kelvin temperatures or new gameplay heat values. Expose the palette/intensity/envelope configuration on definitions so later tuning requires no generic branch.

**Flame lighting (#744).** Flame/smoke content has no scene-light diffuse/specular reflection; radiance comes from configured emission and density extinction. Preserve shell/frame lighting separately. Extend the existing raymarch with front-to-back transmittance/emission integration if extinction is absent, rather than attaching reflective standard materials or replacing the volume with a single facing sprite. Smoke uses alpha/extinction without artificial highlights. The existing unlit shader means the observed defect might be shell light or blending, not a missing unlit flag. Verify against moving lights, dark/bright backgrounds and rotated views before claiming the root cause. Keep bounded sample count and measure cost.

**Flame base (#745).** Expose normalized `baseOffset` measured along world-down from the block centroid, transformed through the contained frame. Start at 0.60 of the interior half-extent below the centre (existing shader base is 0.45); both variants share this setting unless explicitly configured otherwise. Account for volume clipping as the cube turns. The flame's rise remains world-up; neither camera orientation nor a chosen local face determines down. Keep enough headroom for the height preset. Test all three primary rotation axes and compare before/after at fixed camera/settings.

## Grass survives until fully buried

The owner supersedes the old clear-on-turn grass rule. A blade remains attached at its stored block-local root/orientation; rotating the block resets the stillness timer for **new growth**, not the existing population. Do not continually project existing roots onto the moving surface. Falling soil does not delete grass; partial burial leaves the visible portion. Delete a blade only when its entire current grown geometry is on the wet/soil side of the published surface, within a small numerical tolerance. Query all triangle vertices against the current planar `liquidSurface` (including base width/lean), not only the root or tip; a future nonplanar provider supplies the equivalent containment query. Camera occlusion by the shell is not burial. Rendering depth handles covered fragments; don't remove a blade merely because it is offscreen.

Reuse the inclusion pool; retire fully buried slots and allow new blades after stillness/surface readiness under the existing delay/growth limits. Cosmetic state need not enter game saves. Test falling surface, partial/full cover, rotation without burial, growth-in-progress and camera-only movement. This is a deliberate visual behavior change, separate from earth gameplay.

## Profiler animation fidelity (#752)

Every recipe supplies the same registered appearance update **and pre-render pass** capabilities as its production host, not merely a scene mesh and ambient `blockEffects`. Advance contained simulations/shader clocks/part animation during warm-up and sampled frames. Use one explicit presentation clock per run and stable cosmetic seed; no production game RNG/state. GPU samples bracket all contributing passes; CPU samples include relevant updates/submission. Record clock/preset/phase, and include the host's representative lights/environment.

Separate stationary ambient from configured motion phases: use a registered deterministic pose driver for rotation-triggered dust, fluid slosh and similar behavior (initial driver: smooth quarter-turn over one second, one second hold, repeated; reset each sample set). Only recipes declaring motion get that phase; generic code never decides from material identity. Transient effects reset on the declared active sampling window so disappearance doesn't measure empty frames. Reduced-motion tests are separate configurations, not an unnoticed global toggle changing a run. Exports keep phase/unit/count/cohort identity; static and animated rows must not be silently merged. Visual clips plus update/pipeline tests establish fidelity; lack of visible object rotation alone is not proof the existing ambient update loop is stopped. Preserve cancellation, isolation and full coverage under `automatic-profiling.md`.

## Configured music operations (#758)

A music cue is a serializable **ordered sequence of registered operations**, not a scene name interpreted by the service. Define `selectTrack`, `rememberTrack`, `resumeTrack`, `windDown`, `windUp` and filter operations with typed configuration. A track selection references a plan entry containing an explicit list of track handles, `randomNoImmediateRepeat` or `fixed` selector reference, transition settings and optional memory-slot reference. Registered selectors implement policy; missing tracks yield an explicit empty-pool diagnostic/no play, not a different scene's music. Slots such as `tableMusic` are opaque memory handles, not identity tests.

Scene `musicCue` traits hold configured operation sequences/plan references. Mode composition supplies the plan and quiet/ordinary controller behavior; the controller subscribes to scene lifecycle and submits explicit player requests. The ordinary stage plan is the available loop catalog excluding the configured reserved-track list, resolved **at composition time**, not by a generic boss test. Title plan retains the current title track list and only-if-outside-selection behavior; the stage-three scene receives the fixed boss-loop entry through its definition. Resume uses the remembered table slot; wind-down/up are transport operations with the existing spin/crossfade semantics. Preserve current tracks, random-repeat avoidance, unlock buffering, quiet mode, filter behavior and transition timing; cosmetic RNG never affects gameplay.

`MusicPlayer` remains the narrow audio service. `MusicController` becomes an orchestrator driven by these operations; remove scene-named public entry points as consumers migrate, not by keeping a second compatibility policy table indefinitely. `audio-service.ts` owns mixer/settings/unlock plumbing, not scene-to-track decisions. Current `MusicController.stageTrack` is in-memory state; the audited save code does not persist a music cue or pool. Keep it that way: the controller memory slot survives scene navigation within the session, while a fresh Continue uses the normal configured initialization/resume path. Do not add cue/pool persistence or change save version for this refactor, and do not replay historical music events on restoration. Unknown configured operations fail validation at composition, rather than taking a hidden fallback. Tests use another arbitrary plan/scene definition to prove no identity branches are needed and compare existing title/stage/boss/pause/settings/quiet behavior.
