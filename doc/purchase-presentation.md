# Purchase commit projection and success cue (#1214)

This completes the remaining purchase-success portion of #756 and its preserved draft PR #1138. The earlier outcome-sound slices remain delivered; do not repeat them. Preserve purchase validation, prices, payment, received inventory, stock removal, offer-kind behavior and player feedback. This is an immutable commit projection for presentation, **not a new purchase gameplay subscription hook**.

## Authoritative boundary and schema

`GameRun.buyShopOffer` owns the successful purchase mutation and wraps validation, receive, payment, stock removal and rack synchronization in the existing action transaction. The registered offer-kind handler still supplies receive/refusal/price; generic coordination learns no offer kind. Invalid/refused purchases return the existing null result and publish no success. Any throw or invalid result restores state, facts, subscriptions and checkpointed RNG under the existing transaction contract. Do not publish a fact before the complete mutation is committed, or manufacture a success from a state diff.

Record one `shop.purchased` envelope directly through the existing action's immutable recording capability, once per successful single-offer transaction. It carries the standard action/event correlation, sequence, snapshot version and captured run/stage context; subject IDs contain the purchased block's opaque ID. Its payload contains purchased offer/block ID, opaque offer-kind handle, registered destination handle, actual paid price, coins before/after, and the resolved optional success sound ID. All amounts are the validated finite values used by the mutation, not later recomputation. Capture plain values only: no live block, rules, handler, material object or getter. Parent/batch correlation is absent for an ordinary top-level purchase; a future batch feature needs its own documented semantics.

The record is appended after successful receive/payment/stock update and rack synchronization, then exported only after transaction commit via the existing `onCommitted` channel. The new record does **not** enter `lifecycle`, the passive event queue, rack rules or gameplay command dispatch. No current passive reacts to buying merely because its string matches this record. Model listeners retain their existing behavior, and buying an event-listening passive does not let it respond to its own purchase. Adding a real purchase gameplay hook, with subscriber eligibility/order/capabilities, is separately designed future economy work. This explicit boundary avoids expanding gameplay while migrating a sound.

The event envelope's `snapshotVersion` retains the existing action-context convention; this work does not redefine all lifecycle versioning. Captured coins/price are authoritative for this transaction even if another purchase commits before feedback. The successful API return remains the purchased offer for the existing caller; it is not delayed for sound or animation. Failed duplicate submissions publish nothing under normal action identity rules. Save hydration does not replay purchases or success sounds; no new persisted callback or purchase history is needed.

## Configured response ownership

The registered offer-kind definition declares a serializable `purchaseSound` SFX ID, optional to allow intentionally silent kinds. Existing built-in offer kinds explicitly configure `shop.buy` to preserve the current success cue. `GameRun` copies the resolved value into the committed payload uniformly; it never hard-codes the cue or selects it from an identity table. A third-party test kind can supply a different registered ID without coordinator edits. Sound configuration cannot change price, validity or inventory.

The existing configured committed-event sound response consumes that captured sound through its ordinary registered scheduling path, deduplicated by occurrence/action and response owner. No `shop.purchased` identity branch belongs in the generic sound service, and no second purchase-specific listener should duplicate the existing response. Use the shared visual scheduler/presentation clock; this sound starts at the purchase's configured immediate presentation anchor after commit. No animation-completion wait or new timer. A distinct simultaneous purchase remains a distinct occurrence, even if both use the same sound ID. Cancellation, scene subscription disposal, mute and restore follow existing sound/scene contracts.

Remove only the inline successful `playSfx("shop.buy")` from the run controller once its configured committed response is wired. Refusal/click feedback still belongs to existing input/target owners for actions that did not commit; this document does not move all input cues or collapse outcome-completion and scene-entry sounds. Purchase flight remains a separate presenter and never decides whether the purchase succeeded.

## Evidence, alternatives and verification

Source audit at `c611f69`: `src/game-run.ts:buyShopOffer` calls `purchaseVerdict`, registered `price`/`receive`, updates stock/coins and syncs rack without an action transaction. `GameRun.transact` already snapshots state/RNG, records immutable facts and calls `publish` after success; `ActionContext.record` captures an envelope without dispatching passive rules. `GameRun.lifecycle` is different: it delivers model events and records the delivered events. This distinction is why the draft's use of `lifecycle("shop.purchased")` would introduce a new gameplay boundary. `src/offer-kinds.ts:OfferKind` owns price/receive/refusal but has no purchase cue configuration yet. `src/game-run-controller.ts:buy` currently plays `shop.buy` inline after successful purchase. `src/scene-traits/committed-event-sounds.ts` already consumes captured payload sound metadata; its direct service call is a legacy scheduling seam, not permission for another timer or commit-time model sound.

Recording a full new gameplay lifecycle family would be useful for future shopping passives but changes subscription behavior beyond this migration. A dedicated second audio bus or purchase listener duplicates the committed channel. Hard-coding the cue in `GameRun` makes policy generic; inference from coin/stock differences loses causal correlation. A direct action projection plus offer-definition configuration preserves current behavior with the smallest explicit boundary. This documentation makes no claim that the transaction, metadata or scheduling adoption already exists.

Verification: card/passive/item/custom registered kinds; actual paid amount and captured before/after coins; receive/refusal/throw rollback and stock/rack/subscription restoration; duplicate action and rejected purchase silence; event order and deep immutability under later purchases; custom cue and deliberately silent kind; exactly one success occurrence including two rapid purchases with the same ID; existing refusal feedback; no new rack/passive rule invocation (including newly bought listeners); no sound or effects on hydration; shared-scheduler cancellation and scene exit; unchanged flight/inventory/payment. Reuse the existing draft's partial work after rebasing, and report actual checks and browser limits rather than assuming delivery from this proposal.
