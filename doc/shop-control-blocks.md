## Three configured controls, common presentation

Compose a control-block presenter from existing word-cube creation, appearance, inspectable, availability and interaction-feedback capabilities. A scene supplies a list of control definitions: accessible label/description, appearance configuration, layout anchor/size, optional click action, optional drop-target binding and optional ambient-motion configuration. Generic code never chooses behavior from the label, scene, material or control identity. A control with a drop binding is a target because that capability brings its handlers, not because the presenter tests a flag or recognizes BUY.

Buy, Sell and Continue use the same cube proportions, apparent-size family, centered readable face artwork and gentle bounded three-axis precession. Preserve Continue's **paper** appearance. Initial designer defaults use existing Gold appearance for Buy with BUY and a coin motif, existing Steel for Sell with SELL and a dustbin motif, and Paper word artwork for Continue. Motifs are face-artwork configuration, not a new gameplay material or a requirement for a new imported model. The focused shared face-artwork prerequisite supplies these motifs before Buy/Sell integration is accepted; do not omit them silently or create a Buy-only renderer. Label-only cubes can be an intermediate preview, not completion of that artwork requirement. No coin flip, animated bin lid or new action sound is approved in this slice.

The scene declares one shop-associated control row directly below the shop stock: **Buy, Sell, Continue**, in that visual and logical order (#1335). Continue no longer occupies a detached bottom-right corner in the shop. Configure the group anchor relative to the shop region and its spacing/size profile; keep all three clear of stock, the hand and rack. Narrow/short viewports may reflow the group while keeping it immediately associated with the shop and retaining focus order. Actual hit/drop bounds and purchase-flight destinations follow the live control mounts on resize. This changes shop layout only; other scenes keep their own configured Continue placement. Reserve the existing contextual description/deck-count information separately; the Buy block cannot erase “Cards to deck · Passives to rack” or the deck counter. An explicit destination anchor supplied by the presenter replaces reliance on a nested HTML `small` element for purchase flight. Labels/counters remain meaningful information, not substitute visible HTML buttons.

Use one shared control-stage rendering host per composed group, with reusable per-control mounts, rather than a new WebGL renderer for each button. The existing HUD Continue presenter can adopt that group mount through its presenter registry; services must not special-case the shop. Explicitly owned renderer, environment, geometry, texture and frame-loop resources are disposed with the group; individual controls release only their mounts and owned resources. No code in `main.ts` owns layout or actions. A transparent overlay only receives input over registered control hit regions; it must not intercept drags elsewhere.

## Independent motion and feedback

Use the shared precession trait's dedicated orientation node, separate from layout/spring placement and inner hover/press scaling. Reuse its bounded rest pose, amplitudes, periods, reduced-motion policy and shared ambient frame/clock. Actual hit tests and projected drop bounds follow the composed transform. Cover suspends motion; exit disposes it; resume creates no duplicate controls. Per-frame idle motion is not a finite-event scheduler queue and cannot delay outcomes.

Normalized hover/focus, valid/invalid drop and press states arrive from the existing interaction/source/target owners. Present accepted hover with the standard modest lift/scale; refusal with the existing configured unavailable/refusal appearance and description, plus the existing denial cue at its authoritative owner. Successful purchase/sale/navigation keeps its existing sound owner, exactly once. A generic appearance capability consumes the state; it does not run purchase validation or inspect a material/owner kind.

## Preserve Buy and Sell ownership

Buy remains a drop target for the offer sources already admitted by their configured handlers. Existing purchase verdict, affordability, rack/deck destination, payment, stock removal and flight semantics remain authoritative. Replacing the HTML target changes target presentation and destination anchors, not purchasing rules. A labelled cube is not a new “buy selected item” click action; keep the existing drag/source actions and their accessible equivalents.

Sell remains the existing installed-item sale target in the shop. Shared discard/sell mechanics retain their source/target ownership and existing refusal rules. Configure this presentation on the shop's Sell target without unilaterally changing the normal-play Discard control or its click behavior. The shared bin service receives an explicit presenter/description from its composing scene; it does not branch on phase to choose a renderer. A later Discard block adoption can reuse the capability as its own focused delivery. No sale/collection policy moves into the visual cube.

## Continue: click and explicit drop action

Continue is still a navigation action, never stock or an item. Click, keyboard and accessible activation dispatch the existing Continue command once. A carried object dropped on Continue also invokes that same command, through a reusable **return-source-then-invoke-action** drop-target handler. This is the designer's explicit interpretation of the owner's requested “drag to Continue”; it does not implicitly buy, sell, discard or consume the carried object.

The target first uses the source's standard ended/cancelled return-to-owner settlement, then invokes the configured navigation command only if that settlement succeeds and the current action remains available. The source retains its authoritative ownership throughout a visual drag. Do not wait for a return animation to finish: presentation may be cancelled by scene exit. If the source cannot safely return or the target is unavailable, reject through the normal path and remain in the shop. Bind the handler to the configured sources admitted by the shop input composition, not a name test in the adapter. Lost capture/cancel does not invoke navigation. A tap or a drop must not additionally fire a synthetic second click.

Leaving keeps existing unsold-stock/confirmation rules. A carried unsold offer returned before leaving remains unsold; it is not a free purchase. An installed item remains owned, not sold. No refund/payment/deck/rack rule or save-format change is introduced. Include this explicit behavior in the Continue inspection description so the player can tell it is an exit target. This resolves the earlier unspecified Continue-drop question. The concrete missing source acknowledgement is supplied by [the source-settled drop protocol](drop-settlement.md); its shared protocol and admitted-source adoption must land before this target, rather than inventing an owner branch.

## Access, lifecycle and validation

Remove the superseded visible HTML Buy/Sell controls and duplicate visible Continue button, but retain semantic DOM controls/target descriptions needed for keyboard and screen readers. Settings sliders/toggles may remain HTML. Broader removal of menu buttons is tracked separately by #463 and does not remove informational labels or meaningful form controls.

Controller traits own group lifetime, availability and command wiring; services draw supplied controls. On cover/exit, unregister targets, cancel active source/target paths through their existing owners, remove listeners and settle effects once. Scene teardown never leaves a phantom target or late click; re-entry mounts one set. Reduced motion keeps a readable rest pose and normal input. Runtime tickets must cite the merged control and precession contracts and keep implementation separate from their design PRs.

These are reuse seams, not evidence that the new grouped control renderer or Continue-drop handler already exists. Three independent canvases would be locally easy but multiply lifecycle/context cost; a shared stage and configured mounts avoid that. A visual-only conversion that silently drops the deck counter or changes source rules misses the agreed behavior.

## Standalone menu blocks: no HTML enclosure (#1364 / #1366)

**Owner default:** every menu/control block is visually standalone. Its mounting or input element has no visible HTML border, panel, button background, backing rectangle, radius/shadow ornament or separate target box around the block. The shared presenter and configured layout own this treatment; do not hide the defect with three label/scene selectors. Transparent HTML structure is still permitted for layout, hit/drop regions, semantic buttons and screen-reader descriptions. A keyboard focus/hover/unavailable indicator remains on or clearly associated with the block itself; never remove focus visibility to remove chrome.

The scope is menu blocks, not every HTML surface. Keep settings sliders/toggles and their readable form panel, ledger/information surfaces, contextual captions, deck counts and meaningful descriptions. Block artwork can have its own physical edge/frame; that is not an HTML enclosure. Invisible target bounds remain discoverable through block feedback and semantics, not a dotted rectangle. Do not change action ownership, sounds, payment, sale or source settlement.

**Settings Back:** Home → Settings shows the Back block outside the visible settings form panel. Split the shared form-information surface and its action host/layout outlet rather than removing the settings panel or adding a Settings-name branch. The settings trait composes those surfaces and supplies the normal registered Back action. Preserve scrollable form content, a reachable Back block at narrow/short sizes, focus return and Escape behavior. Do not move other menu actions by implicit scene identity.

**Evidence and reasoning (main `1111027f`).** `src/shop-view.css:.shop-buy-target` still supplies a dotted border/background while the Buy cube occupies a child slot. `src/bin-control-presenter.ts:registerBinControlPresenter` deliberately retains the sale target element around a control-group slot. `src/block-menu/control-group.ts:createControlGroup.place` draws over each owner's current slot bounds; it supports moving slots without changing sale/purchase policy, but it does not itself remove wrapper chrome or group DOM anchors. `src/settings-panel.ts:createSettingsPanel` puts a block-menu items host inside its form panel; `src/block-menu/block-menus.ts:createBlockMenus` binds dialog presentation and configured actions. `src/style.css` already separates transparent/readable dialog treatments. These are reuse seams, not proof that all adopters already support an independently positioned action outlet. The missing form/action split must be added to the shared layout contract, not a one-off DOM move inside an identity-checking service.

**Delivery.** #1335 is the focused shop anchor/group adoption; #1364 removes shared wrapper chrome and supplies the independent form/action outlet needed for Settings Back. If that shared outlet is too large with the chrome change, implementers may split it and retain final delivery boundaries. Both consume this separately merged documentation (#1366); no changes to purchasing/Continue semantics are implied. Old wording preserving the shop's prior lower-screen positions is superseded by the row rule above.
