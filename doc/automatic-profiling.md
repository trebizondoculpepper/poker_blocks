# Automatic full-catalog visual profiling (#663)

**Target extension to #527, not yet implemented.** One **Run all** action discovers the game's registered visual objects, runs an empty baseline and **1, 10 and 50 instances** of every case/phase, and produces a ranked report. No manual per-object selection, count changes or custom browser script is required. Keep the existing selected-case controls for diagnosis; the automatic sweep is the standard report path. This is a developer measurement tool, not an automatic renderer/quality change.

## Evidence and scope

Source audit at `f235339`:

- `src/tools/profiler/cases.ts` already defines registered production factories, optional phases and coverage sources. `uncoveredCases()` only asks installed coverage providers; absent families disappear. Thus an empty coverage result is not proof that every object in the game was measured.
- `src/tools/profiler/runner.ts`, `runCase/run`: currently measures baseline/one/configurable collection, fixed seeds, warm-up, timing availability, hidden-tab retakes and resource disposal. Extend this runner; do not build a competing benchmark engine.
- `src/tools/profiler/room.ts`, `run/listCases/environment`: exposes manual selection and one collection count; no complete multi-count sweep or unattended report path exists. `export.ts` has version-1 fixed one/collection results and sorts one collection, so its schema needs a versioned matrix successor.
- The [executed initial material run on #527](https://github.com/trebizondoculpepper/poker_blocks/issues/527#issuecomment-6822358407), branch `1d3cafc`, completed 34 material cases with zero browser errors, but no GPU timing under SwiftShader and no reflection environment initialized. Rack/menu/effect families were absent. It demonstrates runnable primitives and those limits, not a real-GPU cost ranking or full coverage.

Reuse the existing timer and renderer measurement methodology and primary references in [Visual performance profiler](game-architecture.md#visual-performance-profiler-527). No new timing library is needed. A browser automation adapter may invoke the same public sweep capability for a one-command report; it does not implement its own sampler or assert GPU access just because Chrome launches.

## Automatic discovery and coverage

Each visual-producing definition/factory participates in a registered profiling capability with a representative recipe or an explicit unsupported entry and reason. Family modules enumerate their authoritative registries and register coverage plus factories; generic code only dispatches those capabilities. Do not add a table keyed by material/item identity, scan source filenames at runtime, or teach the runner which object kind it is drawing.

The tool composes a **complete catalog provider set** as part of its developer-mode/bootstrap configuration. Each composed catalog declares expected coverage and its provider reference; validate that the provider is installed, not merely that installed providers report no gaps. A missing provider or missing factory is a reportable coverage failure. New definitions within a participating registry are discovered automatically. A new visual family must bring its profiling catalog capability when introduced; tools cannot discover an entirely unregistered factory by guessing its identity. This is a composition/validation rule, not a special-case list inside the runner.

The catalog includes registered materials and derived/container variants; passive and usable rack items; rankless/container blocks when implemented; letter, word and menu blocks; registered optics alternatives; and composed ambient, activation and exit visuals. Existing material cases #620, rack #621 and visual #622 supply the recipes: extend their contracts instead of duplicating them. Only installed/built appearances can be rendered; planned v3 or unfinished gameplay objects appear as unavailable where declared, never as fabricated successful measurements. Shared environment/background renderers, if visually profiled, bring their own explicitly labelled host cases rather than being attributed to one block's mesh.

One case is a typical representative configuration, not every possible string/font/card/colour combination. Declare representative variants and phases where they change the render path. A word/menu group counts as **one group**, with its letter/block count recorded; one particle-effect instance means one complete configured emitter/exit effect, not one particle. Every row records that unit so comparisons cannot disguise an arbitrarily large object as a single block. Transient phases reset from seeded state and use a declared sampling window; an exit must not disappear early and then measure empty frames as its normal active cost.

A complete report counts expected, available, completed, failed, unsupported, cancelled and uncovered cases/phases. It never displays “all objects covered” solely because the installed coverage providers return no missing IDs. Unsupported entries do not count as successfully measured.

## Sweep and representative host

Default standard sweep: counts `[1, 10, 50]`, 30 warm-up frames and 120 sampled frames per set, cosmetic seed 527, resolution 1280×720 and pixel ratio 1. Record every value; users may choose another preset but the requested standard counts remain one action away. Count 0 is the empty-host baseline, not a visible object result. A baseline can be shared only among cases with the same immutable host/render configuration and sampling epoch; do not subtract an unrelated host's baseline.

Snapshot the catalog and settings before starting, then run one case/phase/count at a time with no preview or other application render loop competing for the benchmark renderer. Use production creation/update/disposal paths and preserve deliberate sharing. The host configuration supplies camera/layout, lighting, reflection environment, tone mapping and output colour space, antialiasing, canvas/drawing-buffer sizes, transparency and expected ambient animation. Initialize reflective looks using a renderer-owned representative environment rather than borrowing a texture from another WebGL context. Register different host capabilities where normal production paths differ; the runner must not select them through object identity checks.

Use the documented fixed-grid collection layout and camera framing for each count; retain each object's fixed orientation/seed across comparable runs and record camera/framing/object scale. Fitting more objects into one viewport changes their per-object pixel coverage. Report framing/coverage metadata and interpret the series as a **fixed-viewport collection test**, not constant per-object screen area or guaranteed linear scaling. Cases needing a different representative host declare it explicitly. Do not silently simplify a production effect to make it fit count 50.

For each count, record warmed GPU median/p95/sample count and rejected queries where available, CPU update/submission median/p95, frame median/p95, draw calls/triangles, resource counts, creation/first-compiling-frame time and disposal residuals. Keep raw and baseline-relative data. Do not average away count identity. Subtraction is an estimate: transmission, shared passes, batching and overdraw can make costs nonlinear. Draw calls/triangles describe submitted geometry, not shader complexity or elapsed GPU time.

Keep execution bounded and cancellable. Each case/phase has a 120-second default timeout, overridable in the run preset; a failed factory/shader/timing set is recorded and resources released before continuing with independent cases. A context-lost renderer aborts the remaining sweep explicitly. Hidden-tab samples are retaken under existing bounded retry policy; exhausted retries become invalid, never zero-cost rows. Export completed/failed progress on cancellation or timeout. Error handling and timeouts belong to the measurement runner/adapter, not game rules. No gameplay commands or run RNG are involved.

## Composable profiler trait (#669)

The automatic profiler is a **composable developer trait**, not behavior owned by Dev 16 or a bespoke screen. Extend the existing registered `devProfiler` scene trait so any developer room can compose it. Its name follows the Dev-prefix rule; do not compose this testing capability into production modes. Dev 16 is the default host and UI example, not a prerequisite or an identity the profiler may inspect. A second configured dev room must run the same trait unchanged.

The trait owns orchestration policy: on entry, prepare the configured host/catalogs, start the automatic sweep and deliver its report. Its serializable configuration supplies catalog-provider references, host/preset reference, counts (default `[1,10,50]`), warm-up/sample frames, seed, resolution/pixel ratio, timeout/retry limits, `autoRun` (default true), report options and registered result-sink references. Optional back navigation/UI settings are host configuration, not required dependencies of the sweep. Settings are captured at start; choosing a later run's settings never relabels earlier results. An explicit manual preset may disable auto-run; standard composition requires no Run button click. The UI can offer Run all again and Cancel.

Narrow measurement/report services own renderer/timer resources, sampling and artifact formatting. They accept an explicit request and return results; they never decide which room starts a run or infer scene entry. `devProfiler` connects lifecycle to these capabilities through registered trait handlers. Results are immutable tool records delivered to registered sinks: for example an on-screen report or a command adapter writing JSON/CSV/HTML. Definitions configure sink handler references, not per-room closures or filename-keyed behavior. Completion is a tool result, not a gameplay lifecycle fact that can award coins or run model rules.

On entry the trait creates one owned run scope and one result delivery path. Repeated frames/renders do not restart it. A deliberate rerun first cancels/settles the previous scope; an entry generation token prevents late completions from changing the next room's report. Exit cancels pending sampling, delivers any partial result under the configured sink policy, detaches listeners and frees owned renderer/objects/timers while preserving deliberately shared assets. A result delivered before exit remains available independently of disposed meshes. Tests cover re-entry, cancellation during asynchronous factory creation and exactly-once completion/partial delivery.

A room composing other visuals supplies a host isolation capability that pauses/disconnects competing rendering while samples run and restores it on completion/cancel/exit. The trait must not test the room's identity to hide specific backgrounds. If isolation is unavailable, the report records that limitation rather than claiming uncontaminated object cost. Catalog and host dependencies are validated before auto-run, with incomplete/unsupported coverage retained in the result.

Both the Dev 16 UI and unattended command compose this same trait with appropriate registered report sinks; the command may use a minimal dev-scene host. Neither duplicates sweep scheduling or count policy. Browser/test harnesses can invoke the narrow runner for unit diagnostics, but that alone does not verify the composable automatic entry/exit/result contract. Source evidence: `src/game-modes.ts` already declares `devProfiler: { backTo }`, and `src/scene-behaviours.ts` currently delegates enter/exit to room show/hide. This decision moves automatic orchestration into that reusable trait and extends its configuration, instead of claiming that the existing show/hide adapter already implements it. Runtime work belongs in #667 alongside the shared matrix/capability foundations #665/#666.

## Automatic report and entry points

At the end, the room displays a report automatically; export does not require interpreting raw rows manually. Include:

- an environment/method/coverage banner, clearly distinguishing hardware, software or unknown renderer and valid versus unavailable GPU timing;
- a full table with one case/phase per row and **1 / 10 / 50** columns for timings, draw calls and triangles, with units and missing/invalid status;
- the most expensive measured **50-instance collections**, ranked by valid GPU median time where available, showing p95 and baseline-relative estimate alongside raw figures;
- a separate **CPU update/submission** ranking and a **draw-call** ranking. If GPU timing is unavailable, lead with the CPU ranking explicitly labelled as such; never rename it “GPU/render cost” or treat it as a proven GPU bottleneck list;
- per-case growth from 1→10→50, observed resource-residual flags and coverage/errors. Do not infer a safe global optimization priority from a software-renderer frame ranking.

Separate block/material summaries from item/group/effect families while retaining the full sortable table. A configurable top-N defaults to ten. Ties use stable catalog order. Missing GPU samples are unavailable, never zero, and do not outrank valid measurements. Limit ranking comparisons to compatible host/method cohorts, or explicitly label different hosts; a full-screen effect and a small card are not an unexplained apples-to-apples comparison.

Export a version-2 JSON schema with counts/sample arrays (not fixed `one`/`collection` fields), environment including renderer hardware/software/unknown classification, source revision, host/config/variant IDs, method, coverage, errors and completeness. Include presentation-friendly CSV and a self-contained HTML summary from those same result records. Preserve version-1 files as identifiable old results; reject unsupported schemas clearly rather than silently misreading a collection as the 50-count sample.

Provide two hosts of the same composed `devProfiler` trait: automatic-on-entry Dev 16 (with **Run all (1 / 10 / 50)** for reruns) and a documented one-command browser run that writes JSON/CSV/HTML artifacts. The command launches or connects to an isolated local test server/browser, records the exact tested revision/settings, reports non-complete runs distinctly and cleans up only resources it created. Exit success requires all expected supported cases completed without measurement errors; a partial report is still saved. A caller can explicitly request a partial/selected run, but cannot claim it is full coverage. Headless/CI results retain software/GPU limitations; no mandatory real-GPU CI gate, new hardware service or scheduled job is introduced here.

This measurement does not automatically choose a cheaper crystal renderer, lower quality or modify production defaults. Optimization/design decisions follow the measured report and visual audition.
