# Crash reporting and manual bug feedback

Design for #1339 / #1342, owner discussion on 2026-11-15. This is a documentation-first target, not a claim that reporting is installed, that a Sentry project is configured, or that delivery has been tested. Runtime and external setup follow separately.

## Agreed experience

Unhandled exceptions and rejected promises should reach Sentry with the original error/stack, the actual shipped version and build revision, browser/version and OS/platform, bounded game diagnostics and recent action breadcrumbs. Include a screenshot when safely obtainable. Sentry should resolve stacks to the matching source, and new grouped errors or regressions should eventually create linked GitHub issues rather than one ticket per occurrence.

Manual reports go through Sentry too. Reuse **Report a bug** beside **Get source code** in the home and pause footers; do not add a prominent game block or a second floating feedback button. The link opens an in-game Sentry feedback form, not the old direct GitHub issue page. The player describes the problem; the same diagnostic enrichment supplies context. An exception is not required and must not be manufactured. A submitted report can be correlated with a specific relevant error when known, never blindly with an unrelated last event.

The source-code link remains an ordinary external link. Report form description is required; name/email are optional, empty by default and never inferred from browser data. Explain that the report includes game diagnostics and, when available, a game screenshot. Allow the player to omit the screenshot. Do not transmit an abandoned form or capture its typed contents as breadcrumbs. Preserve description text on a failed submission, offer retry, prevent accidental duplicate submission and restore focus on close. Report status reflects SDK submission/queue state; a returned event ID is not proof that the server stored it. No screenshot or account login is required to send the description.

## Console entry and phased diagnostic depth

[Console bug reporting](console-bug-reporting.md) adds the owner-approved bare `bug` flow: generated message, existing/easy snapshots and console-free screenshot first; optional literal description/email-in-text later; independent owner-local visual diagnostics afterward. It reuses the common manual reporting controller and preserves this document’s private-data, transport-failure and external-setup boundaries. The console has no description or email prompt; the existing form experience above remains separate.

Primary documentation checked through the Sentry connector on 2026-11-15:

- [Browser attachments](https://docs.sentry.io/platforms/javascript/enriching-events/attachments/) support per-event attachments through event hints and `beforeSend`. Persistent scope attachments accompany later events too: per-report ownership is therefore essential. Attachment storage/access/retention depend on project settings and quota; the game cannot promise availability merely because it generated a file.
- [Source maps](https://docs.sentry.io/platforms/javascript/sourcemaps/uploading/hosting-publicly/) recommends uploading maps ahead of events rather than relying on public fetching. [GitHub integration](https://docs.sentry.io/integrations/source-code-mgmt/github/) supports source/commit linking and native external issue creation. It currently documents automatic issue management on Business/Enterprise plans; our account capability is **unverified**.
- [Browser feedback API](https://docs.sentry.io/platforms/javascript/guides/connect/user-feedback/) accepts manual feedback, optional associated error IDs and attachment hints. Reuse the SDK/widget or a thin custom form adapter; a bespoke reporting server is not the default.
- [WebGL replay capture](https://docs.sentry.io/platforms/javascript/session-replay/#3d-and-webgl-canvases) documents render-loop snapshotting to avoid discarded/empty buffers and notes the performance cost of preserving drawing buffers. This supports a render-owned capture boundary, **not** a claim that enabling Replay automatically supplies a correct composite screenshot of this multi-layer game. Full Session Replay is outside initial scope.

These sources establish feasibility, not installed SDK compatibility, account entitlement, reliable phone performance or an end-to-end delivery result. Implementation must verify the current SDK against Vite Plus and the actual renderer; no new package/version is selected solely by this document.

## Ownership, configuration and composition

An application-lifetime configured reporting controller owns **when** to collect and submit diagnostics, bounded breadcrumbs, manual report requests and associated-event selection. It obtains narrow read-only provider and capture interfaces. Configuration supplies environment enablement, public DSN, release/build identifiers, allowed diagnostic sections/fields, size/count limits, rate policy and feedback form options. Keep app reporting enabled across scene transitions without accumulating one global handler per scene. Compose its host lifecycle explicitly; `main.ts` constructs and connects capabilities only, with no reporting policy.

The Sentry adapter initializes the supported SDK once and mechanically submits envelopes/feedback, tags and attachments. It knows no material, mode, screen or gameplay outcome. Use the SDK's global error/rejection capture rather than registering an additional competing handler that duplicates the same exception. Handled exceptions are reported only through an explicit owner request; reporting is never used to decide score, repair the model or delay transitions.

Diagnostic owners register their own bounded plain-data contributions and unregister on disposal. Generic collectors dispatch providers and never infer game state by diffing, inspect a material identity, or treat traits as flags. Provider exceptions become failed sections without recursively reporting new errors. Reentrancy guards, queue/byte limits and rate limiting bound error storms; transport/attachment failures do not recursively capture themselves. Preserve the original exception as the primary evidence.

The manual action opens the form through the same reporting capability from any configured footer. Its original game context is captured **before** the reporting overlay changes scene/focus; submission refers to that report's captured state, not a later run. Snapshot and screenshot timestamps, action IDs when available, build revision and missing-field reasons accompany the report. Do not claim an asynchronously acquired screenshot is exactly simultaneous with the state snapshot. Existing pause-screen behavior remains; the reporting form does not add a presentation scheduler gate or mutate a run.

## Diagnostic payload and data boundary

Capture actual build version plus commit SHA and environment. Browser engine/name/version, OS/platform, viewport and pixel ratio are best-effort SDK/browser evidence, with unknown explicit; do not fingerprint hardware to manufacture missing device details. Mode, scene, round/stage, current/target score and active action are reported through their owners as opaque data. Source map/release correlation must identify the exact deployed artifact, including development build differences.

Reuse snapshot limits above as initial configurable defaults. The production schema explicitly allowlists useful card zone/identity/material/bonus and passive-instance summaries plus scheduler scope/completion diagnostics. Raw `traits` objects and callback serialization are not a production data contract. Include relevant counters/lifetimes as plain provider descriptors, not arbitrary object graphs or full saves. Unavailable sections and truncation travel with the report. This is diagnostic evidence, not an import file or deterministic replay guarantee.

Recent breadcrumbs are bounded semantic actions/commit identifiers and errors, not raw pointer movement, text keystrokes, clipboard contents or network bodies. Opening/submitting/cancelling feedback uses the existing UI sound conventions; diagnostics captured automatically are silent. Do not register a user action as a crash simply to obtain a stack.

Exclude cookies, auth/storage contents, credentials, form text except the explicitly submitted message, sensitive URL query values and unrelated page DOM. Disable automatic personal-data enrichment unless a separately documented need is agreed. The source archive/maps uploaded by CI contain shipped source only, with no `.env` or private files. Bound and scrub both event fields **and attachment bytes**; do not assume SDK event scrubbing redacts arbitrary JSON/image attachments. Automated public GitHub tickets contain an allowlisted summary and Sentry links, not raw diagnostic attachments or user contact data.

## Screenshot contract

Screenshot acquisition is best-effort and separately bounded. The renderer owns freezing/copying its back/front canvases at a valid rendered frame; a compositor accepts those copies plus approved HUD/menu content. Do not capture the feedback form/contact inputs. Share the existing layering convention, but use a configurable bounded resolution/byte budget rather than mandatory 4K or GPU stalls. No continuous Replay recording, global `preserveDrawingBuffer` change or per-frame image encoding is authorized by this design.

For an automatic exception, attach an image only if a valid bounded capture is obtainable through the current renderer capability without making error submission depend on another frame. If capture requires a future frame after rendering has crashed, submit the error immediately with screenshot unavailable. Do not re-enter a failing render from an exception hook. A later frame or stale image must be identified as such, not represented as the failure instant. Context loss, tainted canvas, encoding failure, missing host, image-size limits and unavailable capture all produce an explicit reason and never drop the error.

For a player-initiated form, request capture before showing the form and let the form proceed regardless. An available preview can be omitted. Never replay gameplay or advance simulation to manufacture an image. Attachment resources are owned by that report, released after submission/cancellation, and never leak into a later error through a persistent scope. Verify that capture does not leave renderer size/pixel ratio altered. Measure capture cost on desktop and an actual mobile device; no performance improvement is claimed.

## Source linkage, credentials and environments

The public client DSN is configuration, not a login/tracking cookie. The owner supplies the target project/organization and region. Private Sentry auth/upload tokens belong in ignored local environment or CI secrets and never a GitHub comment, browser bundle, committed file or screenshot. Avoid printing secrets while verifying configuration.

Build/release work generates and uploads matching source maps/artifacts using the supported current Sentry/Vite tooling and the same shipped release/build revision. Establish a documented CI/local behavior when credentials are absent: ordinary developer builds remain usable with reporting disabled; a release job explicitly required to upload maps must fail clearly rather than claim stacks are readable. Restrict repository access to this project as appropriate and record the permissions requested by the chosen integration. Do not enable Seer/autofix, auto-merge, billing upgrades or full Session Replay as a side effect of basic error setup.

## Sentry to GitHub intake

Use Sentry as the diagnostic system of record. Configure native GitHub integration/alerts when the actual plan supports them; otherwise return a concrete option to the owner before building or deploying a webhook service. Distinguish manually submitted feedback from automatically grouped exception events. Manual feedback can create an individual triage ticket; automatic exceptions create tickets for newly actionable groups/regressions under a configured repeat-suppression policy. Do not assume default integration grouping/retry behavior meets this: test repeats and concurrent deliveries, and retain a Sentry-group/external-issue association so duplicate events do not open an unlimited stream of tickets.

A generated ticket includes report kind, concise message, Sentry group/event link, time, release/build, environment and browser/platform summary. Link to private diagnostics rather than copying attachments into public GitHub. Preserve feedback/error association without collapsing independent reports merely because a generic title matches. Add agreed bug/triage labels through integration configuration; automatic reporting cannot declare an issue ready, claim it, invent complexity or override existing agent ownership. Triage consumes the resulting ordinary GitHub issues. A failed GitHub action leaves the Sentry report available and does not affect gameplay.
