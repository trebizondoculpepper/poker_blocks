# Gameplay lifecycle and context opportunities (#615)

Research report, 2026-11-12. Inspected revision: `adfb8a87441e41500461cb24d033b178555b4dd0`. This is evidence and recommendations for architecture #611, **not an implemented API or approval of the illustrative modifier rules**. Spatial game design #616 remains parked. Research was a local source audit plus a bounded geometry probe; no external library or general event-system replacement is recommended here.

## Findings and recommended direction

The opportunity is broader than material reactions. A shared model lifecycle can support economy, ownership, ordering, state, spatial and progression modifiers through the same registered rule/command mechanisms. Hook breadth should grow by declaring a meaningful committed fact or explicit mutable phase, rather than by adding item-specific callbacks to the run controller. A hook and the context it permits are separate capabilities.

Reuse the existing event-rule registry and command runner, extend their coverage and listener ownership, and compose `materialEffectsController` onto the playfield as their client. Do not introduce a second gameplay event bus. The visual scheduler remains separate: it presents captured outcomes, never evaluates these rules later. The generic gameplay coordinator exposes phases; individual configured traits supply effects and queries.

“Cheap hooks” is an achievable goal, not zero-cost execution. Existing `PassiveEventQueue` already indexes listeners by event type: emission appends an event and delivery looks up that event's listeners. Do not replace this with a scan of every definition on every action. Allocation, context capture, rule evaluation and commands still cost work. Avoid constructing an expensive context before discovering that anybody requests it.

## Hook opportunity catalogue

Names below are **proposed families**, not a requirement to implement every name or a claim that spelling is final. #611 chooses canonical names and reconciles existing `discard.completed`, `block.removed` and other events without double delivery. Each completed fact carries action/event identity, source/cause, relevant before/after snapshots and the affected ordered instances. Commands and mutable working values are available only at documented mutation points.

| Family and authoritative moment                         | Useful context                                                             | Illustrative creative opportunity                                                                                                  |
| ------------------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Action validation/request vs committed action           | Requested operation, verdict, allowed target                               | Eligibility modifiers belong in explicit validation policy; refused gestures must not accidentally farm successful-action rewards. |
| Placement resolution, then placed batch/per-block facts | Ordered original placements, cells, resolved replacements, first placement | First-placement effects; neighborhood or growth-direction bonuses.                                                                 |
| Opening/replacement committed                           | Wrapper/source and adopted contents; cause, same-cell mapping              | React to opening a Present without generating contents twice or treating opening as destruction.                                   |
| Before whole-field scoring                              | Resolved field version, plays remaining, eligible traits                   | Material upgrades, countdown deductions and optional requested global geometry metrics.                                            |
| Before contributor value / line operations              | Chosen scoring scope, contributors, working score                          | Contextual block/line modifiers; preserve scored-subset eligibility and existing operator ordering.                                |
| Line finalized / all lines finalized / total applied    | Immutable line results and aggregate                                       | Reward crossing lines, diversity of axes or multiple qualifying hands without rewriting a finalized result.                        |
| After scoring, before terminal settlement               | Finalized score plus updated model field                                   | Explosions/bonus transfers affect future state, never retrospectively change this play's score.                                    |
| Discard batch and optional individual facts             | Ordered removed cards, allowance used, old/new zones                       | Existing Scrapper-like rewards; separate “once per action” from “per card” explicitly.                                             |
| Draw/deal completed; deck shuffled/empty                | Ordered actual transfers, deck/hand counts, generation                     | Draw-combination or empty-deck modifiers. Never reroll a draw merely to populate context; #551 owns shuffle/pop changes.           |
| Hand/rack reordered                                     | Old/new ordered IDs, source/destination indices                            | Positional modifier arrangements. Free reorders are potential farming loops; a reward policy needs a separate deliberate design.   |
| Shop stocked / offer purchased / item sold              | Persisted offers, price actually paid, balance delta, adopted destination  | Budget/collection/transaction modifiers; queries and previews are not purchases.                                                   |
| Item used / charge consumed / item exhausted            | Source item, target, effective result and remaining uses                   | Interactions around effective use, without rewarding a refused no-op or spending a use twice.                                      |
| Material/state transformed                              | Same instance, from/to registered state, cause                             | Transformation chains and diversity, while keeping rank/suit and approved reaction timing.                                         |
| Modifier acquired/transferred/reset                     | Effective package, lifetime and source/destination                         | Compositions exploiting temporary versus persistent power, without confusing base values with acquired bonuses.                    |
| Trigger/countdown advanced/zero/resisted                | Before/after count, chain/source snapshot, rejection cause                 | Countdown/resistance modifiers; repeated zero must not repeatedly fire.                                                            |
| Permanent destruction vs removal/retention expiry       | Last snapshot, location, reason, authoritative outcome                     | Loss/aftermath modifiers; normal discard or stage collection must not masquerade as destruction.                                   |
| Card adopted / zone transferred / inventory changed     | Same logical identity, old/new owner/zone, ordered changes                 | Deck-building and retention interactions; mutation owners report outcomes instead of a duplicate mutable inventory.                |
| Reset/reversion completed                               | Reset recipe/result, preserved identity, boundary/cause                    | Respond to approved reset behavior without clearing run bonuses by inference.                                                      |
| Stage start/proposed outcome/final outcome/reward       | Stage rules, immutable outcome and paid ledger                             | Stage conditions and settlement modifiers at an explicit point; not replayed on Continue.                                          |
| Round/run boundary and restoration                      | Boundary kind, saved generation, snapshot                                  | Run/round effects with distinct reset lifetimes. Loading is not a new stage or a successful move.                                  |

A useful event is a model fact or a deliberate rule opportunity, not every setter, pointer move, frame, mesh allocation or audio voice. Rendering hooks can be numerous without becoming gameplay triggers. Stage/scene IDs remain opaque lookup handles; configured trait handlers bring differences.

## Ordering, subscription and safety recommendations

The owner's required outline is placement/reveal → pre-score material actions → scoring → post-score material actions → final settlement. Present contents are fixed at shop stocking; opening adopts that stored payload before material interactions. Countdown deductions precede scoring; detonation follows it. Preserve currently post-score reactions unless an approved rule assigns an earlier phase. #611 must define the exact hook order rather than moving every reaction earlier by analogy.

Compose one material-effects controller onto the playfield, with attach/detach-owned subscriptions to these generic phases. Individual definitions supply registered reaction/command references. A field without the controller contributes none of that behavior; there is no `if (hasMaterialEffects)` path in the gameplay runner. Snapshot listener order before delivery; specify how later changes affect the next event. Reuse existing rack order and registered reaction snapshot semantics. The probe does not authorize arbitrary repeated reaction fixed-point iteration: existing tests expect one reaction-chain step per play.

Distinguish a mutable precondition/working-score phase from a completed fact. A post event cannot rewrite its past. Per-card facts and once-per-action batches need correlation IDs and documented granularity so a modifier does not accidentally pay twice; do not globally deduplicate distinct valid events. Match hooks through registered subscription keys; definitions carry their own settings, not a global item-kind policy table.

Event cascades and trigger-command nesting are related but different: current passive follow-up events are FIFO, while trigger responses are explicitly depth-first. The generalization needs a shared action-level bound/diagnostics, without silently resetting a safety budget at each nested drain. Specify error/failure atomicity and RNG cursor handling before implementation; dropping gameplay commands to stay under a visual budget is not valid. A max-event test is not evidence that all nested paths are bounded.

The current queue's shallow freeze does not protect nested arrays, blocks or mutable trigger visited sets. Capture immutable model views/copies or structurally shared immutable records; keep traversal internals private. A delayed visual reader must not query a newer live field under an older event ID. Save authoritative state, not event callbacks; restoration should rebuild subscriptions without replaying rewards or consuming new gameplay randomness.

## Context providers and cost tiers

Recommend a registered, pure query layer over an explicit **model snapshot/version and scope**. Event listeners request only the queries they need. Cache identical requests within the same immutable snapshot/configuration; invalidate geometry only for occupancy/position changes and material queries for relevant state changes. Do not cache by scene/material identity or maintain a competing mutable field. A lazy closure over live `GameRun.state` is not an immutable query. Enforce hidden-payload visibility: ordinary inspection cannot expose a stocked Present's contents.

Costs below are algorithmic estimates with expected constant-time hash membership, not measured browser frame times. Let n be occupied cells, V the searched empty-box volume, r listeners/rules, and L the line data already computed by scoring.

| Tier                      | Examples                                                                             | Expected work / caution                                                                                                                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Existing event scalars    | Actual price/delta, before/after count, finalized score, source IDs                  | Reuse committed values; constant-size access. Do not reconstruct from unrelated live state.                                                                                                                                                               |
| On-demand simple scans    | Counts, material/state histogram, bounding min/max, inclusive extents/volume/density | O(n); bounds once per requested snapshot. Empty result is explicit, not division by zero. Large-coordinate products need representability checks.                                                                                                         |
| Shared cell-index queries | Six neighbors, occupied-face counts, exposed faces, local adjacency degree           | Cell index O(n) to build; six lookups per queried cell; whole-field exposed faces O(6n). Reuse a snapshot index rather than rebuild per listener.                                                                                                         |
| Existing score context    | Axes, contributor counts, crossings, longest scored run                              | Reuse L. Discovering/re-evaluating lines just to answer a query can be expensive, especially best-hand subsets in long lines.                                                                                                                             |
| On-demand connectivity    | Component count, isolated groups, graph cycle rank                                   | O(n+E), degree at most six for face adjacency. Deletion complicates incremental components. Adjacency graph cycles are not a synonym for 3D tunnels.                                                                                                      |
| Shape comparisons         | Axis balance, elongation, centroid; symmetry under a defined finite transformation   | Simple extents O(n); a fixed number of symmetry probes can be O(n), while unconstrained best-fit searches need their own budget/definition.                                                                                                               |
| Topology/voids            | Sealed cavities, passages, holes; exact/approximate topology                         | A straightforward exterior empty-cell flood fill costs O(V), not O(n). Sparse distant survivors can make V enormous. Require bounded search/sparse or compressed alternatives and clear unknown/budget-exceeded results. Do not call “unmeasured” a zero. |

Use lazy computation plus an advertised query budget/tier. The future design must define deterministic handling for an unavailable/budget-exceeded **gameplay** query; silently changing rewards on slower devices is unacceptable. No expensive topology query should become a compulsory dependency of ordinary placement. Event hooks need not wait for dense/sparse payoff decisions.

## Bounded geometry probe

[Probe](lifecycle-geometry-probe.mjs), [results](lifecycle-geometry-results.json). Run `node doc/research/lifecycle-geometry-probe.mjs`. This is a standalone research script, not a production provider. It uses face adjacency and a padded exterior flood fill capped at 10,000 cells; no timing or mobile/GPU performance claim is made. Sets have unique occupied cells. The probe is intentionally small and not a proposal to flood-fill every production bounding box.

| Shape                                     | Occupied / inclusive box | Density | Exposed faces | Sealed empty cells |
| ----------------------------------------- | ------------------------ | ------- | ------------- | ------------------ |
| Filled 2×2×2 cube                         | 8 / 8                    | 1       | 24            | 0                  |
| Filled 8×1×1 line                         | 8 / 8                    | 1       | 34            | 0                  |
| Flat 3×3 perimeter ring                   | 8 / 9                    | 8/9     | 32            | 0                  |
| 3×3×3 shell missing only center           | 26 / 27                  | 26/27   | 60            | 1                  |
| 3×3×3 with central through-column removed | 24 / 27                  | 8/9     | 64            | 0                  |

Thus density alone does not measure cubical compactness, and sealed-void count alone does not detect a through tunnel. Surface, density and topology are independently useful signals. Whether edge/corner contact, rotation, local versus whole-field scope, temporary cards or a particular kind of hole qualifies is deliberately left to #616. No dense/sparse modifier reward is assigned here.
