# Console bug reports and deeper visual diagnostics (#1461)

Owner-approved sequence: a small API investigation, then a basic bare `bug` command that sends existing/easy game diagnostics and a screenshot, then optional inline description. A separate later extension adds detailed model-to-view correlation. No description prompt, email prompt or other required contact field remains. This document supersedes those earlier ticket suggestions, while retaining the shared [crash-reporting](crash-reporting.md) ownership and external setup gate.

## API findings and limits

The official [Browser JavaScript feedback configuration](https://docs.sentry.io/platforms/javascript/user-feedback/configuration/#bring-your-own-widget) documents `Sentry.captureFeedback` with required `message`, optional `name`/`email`, and hints including attachments. A custom console UI can therefore submit manual feedback without an exception or the SDK's form. Bare `bug` supplies the clearly generated message **In-game bug report**; it must not invent user testimony or manufacture a crash. The [attachment API](https://docs.sentry.io/platforms/javascript/enriching-events/attachments/) accepts a required filename and string/Uint8Array data, with explicit MIME type. Use report-scoped feedback hints for JSON and image attachments, not sticky attachments on a global scope that could leak into a later unrelated report. A JSON snapshot and supported screenshot are report attachments. Disable unrequested replay capture; this feature does not approve continuous Session Replay.

This verifies API capability, not the current account configuration, installed SDK or server receipt. Use the configured shared Sentry adapter; do not add a REST uploader or expose a private API token in the browser. Keep the project/DSN/credentials gate on #1339. SDK acceptance/queueing, transport failure and unknown receipt are distinct; an event ID or successful queue flush alone is not proof of server storage. No automatic email/fix notification or new public issue service is approved here.

## Shared manual-report request

A configured reporting controller accepts an explicit manual-report request with report-scoped description/contact data and requested capture policy. It coordinates registered read-only diagnostic providers and the renderer's bounded screenshot capability, then calls the mechanical SDK adapter with a plain captured report. The service knows no console, footer, scene, material or outcome identity. Capture policy is declared by the caller's composition and registered handlers, not a flag checked to choose source-specific behavior.

Keep the shared request/controller independent of developer-console imports and clipboard. The existing home/pause feedback form (#1348) and console adapter use the same submission/enrichment path; neither owns a second serializer or screenshot implementation. A focused shared submission prerequisite can precede both, so the console does not wait for the entire form UI and production reporting does not depend on developer tools. Existing #1344 SDK/context, #1345 diagnostics and #1347 screenshot capabilities remain prerequisites as actually used.

Each deliberate invocation has one local report occurrence and one in-flight submission. Capture immutable plain data; later model changes do not rewrite the submitted report. Prevent re-entrant/duplicate Return dispatch and automatic repeated submission on re-entry. Retain a bounded pending artifact for explicit retry on failure; do not promise backend exactly-once delivery when the earlier send outcome is unknown. Correlation identifiers let operators identify possible retries. Cancellation/owner disposal invalidates pending UI/capture callbacks, without pretending already queued network data can be recalled.

## Basic command: easy state first (#1460)

Bare `bug` submits without asking for text. Capture the existing available model/scenes/titles/passive/action summaries and version/build/browser metadata, using the shared limits and failure-isolated providers. Missing scheduler/mount/inspection providers must say unavailable. The first command does not build deep visual providers or wait for #1463.

After accepting the command, capture the diagnostic evidence, clear the console's visible log and hide both panel and input catcher, then request the renderer-owned screenshot after those surfaces are absent. Clearing the UI must not clear the captured evidence, gameplay history or diagnostic buffers. A host capture acknowledgement excludes the console without depending on a guessed timeout. Preserve snapshot/image capture times and generation; the report does not claim atomic capture while the game continues.

Screenshot failure, a stopped render loop or unavailable WebGL context cannot lose the state report or hold submission forever. Reuse #1347's bounded capture and no-image reason. Do not pause gameplay, tick a scheduler, advance animations, draw session RNG or change model state to take the report. No new WebGL renderer, UHD/GPU-finish capture or always-on preserveDrawingBuffer is introduced by this command. Its invocation may proceed even when the current game view is broken.

Return a truthful unobtrusive status through the command's existing feedback path. If reporting is unconfigured or failed, retain/report the available artifact and retry state without claiming it reached Sentry. Do not silently send to a different destination. The shared reporting path owns capture/submission lifecycle; the console definition only brings its registered command behavior and presentation exclusion binding.

## Optional description/contact: a later delivery (#1462)

`bug <literal description>` enriches that same request. Bare `bug` keeps its immediate no-description behavior. Descriptions are not evaluated as JavaScript, split at semicolons or stripped by normal command quoting. A registered command input-policy capability parses the literal tail and supplies its own history/echo behavior; the generic runner dispatches it uniformly, never branches on the name `bug`. The prompt-mode proposal is withdrawn; no extra input field or second command stack is needed.

Do not persist raw descriptions or contact information in console history/breadcrumbs. Use a safe command-history representation supplied by the definition, and do not announce private text into diagnostic logs. Preserve the original text privately in the report. Configured length bounds produce an explicit validation/truncation indication rather than silently changing the report.

A deliberately supplied email in the description flags willingness to be contacted about this report. A single unambiguous address may populate this feedback record's optional email field and a report-scoped contact-intent descriptor. It is not verified identity, a global `setUser` update or permission for unrelated contact. Multiple/ambiguous address text remains in the description with an unresolved contact indication, not a guessed recipient. No new account/verification service or automatic message is required. Public GitHub summaries must omit contact details and raw private diagnostic attachments.

The existing feedback form may still offer its optional name/email fields; this console decision does not remove them or make them required. Form description remains user-entered/required under its existing experience, whereas the bare console command intentionally supplies generated text.

## Deeper state: owner-local providers (#1463)

The follow-up adds complete correlation for the declared sections when it fits the diagnostic bounds, with explicit coverage/truncation otherwise. It is diagnostic evidence, not a restorable Three.js/GPU save. Do not serialize live scenes, callbacks, renderer internals, textures/buffers or arbitrary browser storage.

| Owner/provider               | Required plain-data summary                                                                                                                                                                                                                         | Ownership and failure rule                                                                                                                                                                 |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Field/hand visual mounts     | Logical block handle and authoritative field coordinate/zone, current visual mount handle, appearance/model revision, generation, visible state and bounded pose; carried/landing/revealing outgoing leases distinguish live from retained visuals. | The actual visual owner publishes its mapping; never infer identity from rank, appearance name or tree position. Model and visual sections remain distinct so disagreement is inspectable. |
| Scheduler/presentation clock | Current clock pause state/time, existing counts, bounded active/pending work and required scopes with opaque owner/action/generation handles and state.                                                                                             | Pure diagnostic read, no tick/cancel/settle; enumerate only currently owned records. Do not resurrect strongly retained terminal history or traverse weak terminal-status storage.         |
| Passive rack                 | Instance/definition handles, rack position, current saved instance counter/state and associated visual generation/activation state.                                                                                                                 | Reuse authoritative instance snapshot and rack-owned visual bindings; no duplicate counter, reroll or activation on capture.                                                               |
| Inspection binding           | Current inspected source/mount handle and revision, active/closed status and bounded rendered text/provider descriptor.                                                                                                                             | The inspection owner exposes its binding directly; do not scrape arbitrary DOM or trigger a fresh inspection that could hide the stale result.                                             |

The collector requests these providers through the existing registry and records collection time/revision/coverage. Opaque handles are correlation keys, never behavior selectors. Each provider registers/disposes with its service. Exceptions or missing providers become unavailable sections while other sections remain usable. Existing global depth/item/string/byte limits still apply; include total/captured counts and truncation rather than claim a partial list is the full visual model. Larger budgets require measured fixtures and an explicit configuration change, not an unbounded dump.

Implement the independent provider owners as focused slices, then adopt them in the common enrichment composition. They may be built in parallel after this document merges, but #1463's final integration waits for the basic command and its provider children. They enrich ordinary manual reports automatically when composed; no new `bug deep` syntax or separate screenshot flow is approved. Deeper coverage never becomes a blocker of #1460 or optional description.

## Source audit and delivery verification

Audit at `258a47f4`: `src/diagnostics/providers.ts:registerSnapshotProviders` already emits model field IDs/cells and passive instance traits, scenes, titles and actions, but lists scheduler without registering it. `src/diagnostics/debug-snapshot.ts` already isolates provider failure and bounds output. `src/visual-events/scheduler.ts:counts` supplies counts and `status` resolves known scope handles; it does not expose an enumerable detailed debug dump. `src/visual-events/mount-registry.ts` owns opaque channels/generations/retained leases but no public full visual diagnostic list. `src/table-input.ts:showInspection` and its `inspected` binding own table hover/long-press source state, while `src/traits/inspectable.ts` owns the core-block inspection lifecycle; neither currently provides the required diagnostic DTO. `src/console/console-view.ts` owns clear/close/catcher and raw persisted history; `commands.ts` and `command-line.ts` supply registered command execution with semicolon/quote parsing. These explain the reusable seams and concrete missing APIs, not a claim the deeper export is already wired. #1347's screenshot adaptation is still needed; the legacy UHD clipboard capture is not silently reused unchanged.

Verify basic submission with no user text, easy-state unavailability, no DSN, one-shot retry/unknown queue outcome, console absent from a nonblank screenshot, screenshot failure retaining state, teardown and unchanged state/RNG/clock. Verify optional literal text (including semicolons, quotes and JavaScript-like strings), no execution/history leakage, no contact, one clear address and ambiguous addresses. Deep fixtures reproduce stale Present wrapper versus adopted payload, missing mounts, passive counters/activation, stale tooltip source, required scope progress and cancellation; prove no live-resource serialization, limits/coverage, disposal and missing-provider isolation. Unit/adaptor tests are useful without credentials; live acceptance later requires a real private Sentry report with expected state/image/contact fields and matching build/browser context. No server delivery is claimed by this documentation.
