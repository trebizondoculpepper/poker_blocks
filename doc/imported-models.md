# Shared imported-model preparation and presentation (#1184)

Concrete target for the common gap reported on #747/#748/#753/#1049–#1051/#1056. Reuse [the approved asset budgets and provenance](presentation-contracts.md#asset-processing-and-replacements-747-748-753-759); this document supplies the preparation profile, asynchronous resource ownership and registered factory interfaces those imports need. Asset selection remains the owner’s existing choices in `CREDITS.md`. A missing local exporter is tooling work, not another owner approval gate.

## Offline preparation: registered source preparation providers

Choose a registered source-preparation provider explicitly in the maintained local command. **Headless Blender** handles native `.blend`, FBX and OBJ; a direct **self-contained GLB** provider handles owner-supplied GLB without requiring Blender (#1442). Both emit the same validated static-parts profile and provenance manifest. A GLB provider does not claim to import native Blender/FBX/OBJ. `gltf-transform` is not required or silently introduced as a dependency. The [official CLI](https://docs.blender.org/manual/en/latest/advanced/command_line/arguments.html) documents background operation, disabled automatic Python execution, script invocation and a nonzero Python-error exit code; argument order matters. The maintained exporter controls source loading with embedded auto-execution disabled. Never run scripts embedded in a downloaded project/archive.

Provide a versioned local preparation entry point under `scripts/models/` that accepts source path, output directory and explicit profile/config. It records the selected provider, actual tool/Three.js version, script revision and complete parameters (including Blender version when that provider is used). The selected Blender provider configures a compatible executable or reports a concrete environment failure. The direct GLB provider does not require installing Blender; missing source files remain explicit asset-input blockers. A missing executable does not justify pretending a different source format was converted. Do not claim a binary is installed merely because this contract chooses it.

Before modifying an asset, record source/archive SHA-256, selected source URL/creator/licence, supplied notices, file inventory, node/mesh/triangle/material counts, texture dimensions, bounds and orientation. Keep original source or its verified manifest outside the shipped bundle. Extract nested archives as data with confined paths; the exporter runs only the maintained project script. For `.blend` loading, disable source scripts/drivers under the supported API as well as CLI policy. A recorded local Downloads path is intake evidence, never a runtime URL or proof that another checkout has the source.

The initial output profile is **static mesh plus explicitly named parts**, packaged as a validated self-contained GLB and plain manifest. Bake static hierarchy transforms, normalize the logical object to its documented unit bounds/pivot, preserve normals/UVs and retain only explicitly declared moving part mounts. One primary mesh may contain material groups; additional flat mesh parts have stable opaque node references/local transforms and optional authored pivot metadata. No arbitrary skeleton, source scripts, hidden cameras/lights or animation clips enter this profile. Unsupported content fails with an actionable processing report, not a half-loaded model. Use ordinary embedded textures and geometry initially; do not require Draco/KTX decoder downloads or external source URLs at runtime.

Retain the existing starting budgets: 2,000 triangles, two material slots and textures at most 512×512 per repeated logical object, adjustable with measured silhouette/readability evidence. Simplify/bake only as needed; thin hat folds, fan blades and die face markings require inspection rather than blind decimation. Record before/after counts, modifications, color-space/normal/roughness choices and tool parameters. The manifest includes overall bounds, primary/part references, source and processed revision/checksum, texture/material inventory, credits/notice paths and any explicit budget exception. Do not infer a part’s animation from its name: definitions bind a role to a node reference and registered behavior.

Every distributed asset/adaptation retains the recorded source/creator/licence/modification information and upstream notices under the existing credits process. The importing PR moves the matching `CREDITS.md` entry from Selected, pending to Shipped with actual paths and modifications. Do not copy a claimed licence from a source filename or treat this architecture decision as provenance verification. D20’s recorded ShareAlike requirement remains its asset task’s explicit distribution check; unrelated code licensing is not changed here.

Preserve normals/UVs/materials/embedded texture color-space semantics and explicit part references/pivots. Never infer a moving role from a node name or invent missing selected geometry. Reject unsupported skins/animations/cameras/lights/extensions/external dependencies with a concrete report; do not silently drop content to make validation pass.

Use the **installed Three.js GLTFLoader and GLTFExporter add-ons** in a bounded owned local browser preparation harness. The existing `scripts/profile.ts` demonstrates local server/isolated Chrome startup, bounded result collection and cleanup of only owned processes. Reuse/extract that mechanical lifecycle rather than maintaining a second copied browser controller. The provider has its own tool entry module, not the game bootstrap or a game-mode identity branch. GLTFExporter is called with explicit binary output; its default is JSON. This is offline tooling only, not a runtime conversion or a new parser dependency. Local code inspection of `node_modules/three/examples/jsm/exporters/GLTFExporter.js:parseAsync` and its installed types establishes the supported asynchronous binary option; `src/visual/model-cache.ts:staticPartsBlueprint` supplies reusable static-profile checks and transform-baking evidence. These are API/source findings, not a claim a selected GLB has already converted successfully.

Preflight the binary/JSON references before loading: no remote texture/buffer URI or arbitrary source-script execution. Serve only task-owned source/output paths through the bounded harness; keep source archives outside dist. A supplied file is data, not authority to fetch unrelated files or run embedded code. Record original and output SHA-256, exact source/creator/license/notice evidence, tool version and parameters, bounds/pivot/part references and before/after triangle/material/texture counts. Validate emitted output by reloading it through the same declared profile, not merely testing that an ArrayBuffer was returned.

Retain the 2,000-triangle/two-material/512px starting budgets and selected-artwork quality requirements. The direct path need not implement automatic decimation or texture baking: report a budget/profile failure with actual counts, then use an appropriate separately configured preparation provider or an evidence-backed exception. Do not silently approve oversized assets or claim the source format alone makes them lightweight. No asset, license or file availability is invented by this rescope. Blender stays available when source conversion or authoring requires it, but it is no longer a prerequisite for a valid supplied GLB.

#1192 becomes the focused command/direct-provider/manifest delivery; source-specific conversion additions may be split if independently sizeable. Asset preparation/adoption tickets wait on actual supplied files and this capability, not an unnecessary Blender-install permission question. Verify a small actual GLB, embedded textures and parts, normalization/orientation, deterministic manifest fields (separate timestamps), unsupported/external content, budget failures, output reload, failed/cancelled harness cleanup and production-bundle exclusion. Supply a turntable and exact counts before any asset task is marked shipped. No unreviewed source asset, executable download, license change or runtime loader redesign is approved here.

## Prepared asset provider and cache

Use the **installed Three.js GLTFLoader add-on**, not a second rendering library. The [official loader documentation](https://threejs.org/docs/pages/GLTFLoader.html) describes the explicit add-on import and asynchronous load/parse API. Register a provider for the validated static-parts profile. The definition supplies an asset/manifest handle and revision; the provider never chooses from a material/item identity table or guesses an effect from a filename.

A renderer-context-owned cache coalesces preparation for the same asset revision/profile. Its entry owns the parsed immutable geometry/textures/base materials, validation metadata, pending request and reference count. Consumers receive a prepared blueprint lease, not ownership of the shared buffers. Different rendering contexts cannot share mutable capture/environment targets. Raw file bytes may use ordinary transport caching; no cross-context render target or global mutable “current model” is allowed.

Fetch only the bundled self-contained asset and validate the profile/manifest before exposing a ready handle. A cancellable fetch may feed `parseAsync`; do not promise that a loader promise itself can abort parsing. When the last consumer leaves during preparation, cancel what can be cancelled; a late parse completion with no live consumers must dispose its results rather than mount. Concurrent consumers retain their own leases; cancelling one does not abort another’s valid preparation. Failure removes or marks the failed entry with explicit retry semantics, keeps the declared fallback and reports a diagnostic. No permanent unresolved promise can hold input or a result scope open.

The cache releases parsed geometry, texture and decoded-image resources under the provider’s ownership contract when its last lease/context ends. An instance never disposes another instance’s shared geometry or texture. Per-instance stateful material clones/feedback bindings are explicitly owned and released with that instance; immutable textures/program source remain shared. Verify release against the loader’s decoded-image resources rather than relying only on scene removal. Cache keys are resource/revision/context handles, never behavioral tables keyed by a material name.

## Registered adapters for current visual interfaces

`PassiveVisual` and `BlockAppearance` currently supply primary geometry/materials plus flat extras, not arbitrary glTF scene roots. Adapt the prepared static-parts profile to those existing shared builders instead of rewriting every host to understand a model hierarchy. A registered imported-model factory supplies normalized primary geometry, explicit additional meshes, whole-object bounds, pick/outline geometry and named part mounts. Passive definitions select it through `visual.builder/config`; material appearances select their registered assembly/config. The same definition and adapter are consumed by rack, shop, inspector/browser, hand and field as applicable. A second model is another asset/config, not another renderer.

Loading is a presentation preparation capability: a definition also supplies its current-artwork fallback. Prepare asynchronously, then swap the **appearance channel** through the generation/revision-checked mount/projection contract, preserving pose, input ownership and captured interaction state. The existing mount registry (#1163) provides opaque channels/leases; it does not itself free GPU assets or make these builders asynchronous. The adapter owns that preparation/binding bridge. Source removal/scene exit invalidates the pending consumer; a late model cannot replace a new occupant or resurrect a card. Restore renders the current definition without replaying activation/model commands.

All visual instances use a uniform owned-resource/disposal capability. `PassiveVisual.dispose` already supplies a seam; the card adapter must replace blind disposal of shared imported geometry with the same explicit ownership handoff, applied uniformly through the appearance builder rather than `if imported` checks. Existing procedural builders keep their current owned-resource cleanup. Imported instances release cache leases and their own material clones/part transforms, never the cached asset prematurely. Extend this normalized lifetime interface in the shared builder/consumer, not via per-host special cases.

Rebind the declared selection/activation/transition feedback to the newly prepared appearance and reapply the current presentation state without restarting gameplay. Use [appearance-owned selection feedback](game-architecture.md#appearance-owned-selection-feedback-1153); a GLB material is not evidence that every generic caller can write `emissive`. Registered prepasses belong to the host as usual. Supplemental geometry participates in bounds, hit testing, outline/feedback and disposal; an invisible pick proxy is never rendered as a surrounding cube. No extra logical cells, altered mass or collision rules follow from asset detail.

For moving parts, a separately registered part-animation capability takes an opaque part mount, axis, pivot, speed and reduced-motion policy from the definition. It advances on the shared ambient presentation frame/clock, not a new timer or finite scheduler queue. Air’s selected two fan units share prepared resources; only configured rotor mounts spin at the already documented initial 1 revolution/second, while housing stays fixed. A source containing only one mesh does not prove separable rotors: offline processing must author/verify the parts or record the permitted faithful reconstruction. No visual factory tests a node name to decide it is a fan.

Per-item loaders would duplicate cache, cancellation and ownership policy; offline-only procedural approximations would miss the selected-asset request. Supply real source/processed turntables, host screenshots and measured 1/10/50 rendering/resource costs. ## Prepared visual mounts: explicit host bridge (#1387)

The model cache is a delivered resource service, not a mount abstraction. Source audit at `d925ff33`: `src/visual/model-cache.ts` supplies renderer-scoped blueprint leases; `src/passive-visual.ts:PassiveVisualBuilder` is synchronous/context-free and returns geometry/materials/extras; `src/passive-rack.ts`, shop offer construction and `src/tools/object-browser.ts` each construct visual meshes. `src/rendered-blocks.ts:dispose` directly frees appearance geometry/materials/textures. Therefore passing a cache lease into current builders alone would either leave no async host update path or let an existing consumer dispose shared assets. The following bridge must precede #1194/#1195 import adapters.

Keep logical mounts stable and replace only their appearance channel. A host supplies an opaque renderer-context services object, parent/pose mount, current generation/revision and registered feedback/prepass outlets. Shared mount helpers install the returned visual parts, bounds/picking/outline contributions and lifetime; logical identity, input/source ownership, transform and current presentation state stay on the outer mount. This is a common ownership protocol with passive/card adapters, not a universal game object or identity-keyed host table.

Normalize every visual's resource release to an idempotent lifetime handle. Procedural builders adapt their current owned geometry/material/texture cleanup; imported builders release blueprint leases plus owned material clones and instance parts. Hosts invoke the handle uniformly and never inspect an imported flag, inspect material class to decide ownership, or recursively dispose all visible resources. Borrowed immutable buffers remain cache-owned. Existing explicit extra/edge/prepass resources must each have one named owner; disposing one instance cannot invalidate another.

First consolidate passive mounting over that lifetime protocol, preserving current procedural visuals and every host's existing behavior. The common passive mount builds the primary/extras, binds registered feedback and host prepasses, and exposes a stable appearance replacement outlet. Rack/shop/browser/profiler adopters supply their own anchors and interactions, not four copies of construction/cleanup. Keep activation/selection state outside the replaced child and reapply it through compatible registered providers; no new generic emissive/color assumption.

Then extend configured visual builders with renderer context and optional **preparation registration**. A builder produces its ordinary fallback immediately and may return a cancellation/release handle plus a ready candidate. A ready callback carries the requested revision/generation; the mount accepts it only if still current. Preparation failure retains the declared fallback and reports a bounded diagnostic. The host atomically unregisters old prepasses/feedback, installs the candidate and rebinds current state before releasing old resources. If installation fails, release the candidate and retain or restore the valid fallback; do not leave half an appearance mounted. Preparation never holds model/input/result scopes open and never replays activations on restore.

Cards adopt the same lifetime/preparation protocol through their existing appearance builder and mount helper. Preserve board/hand material handover, face print, extras, pick bounds, ghost/mask routing and revision cancellation. Do not silently invalidate a flight/exit's leased captured visual: outgoing captures retain their own appearance lease until their documented end, independently of the live mount's replacement. A late result after removal, reset, host disposal or changed revision releases itself and cannot mount. Renderer context disposal invalidates all its preparation registrations before cache teardown.
