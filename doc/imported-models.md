# Shared imported-model preparation and presentation (#1184)

Concrete target for the common gap reported on #747/#748/#753/#1049–#1051/#1056. Reuse [the approved asset budgets and provenance](presentation-contracts.md#asset-processing-and-replacements-747-748-753-759); this document supplies the preparation profile, asynchronous resource ownership and registered factory interfaces those imports need. Asset selection remains the owner’s existing choices in `CREDITS.md`. A missing local exporter is tooling work, not another owner approval gate.

## Offline preparation: one maintained Blender entry point

Choose **headless Blender** as the required source preparation tool, because supplied inputs include native `.blend`, FBX and OBJ; a glTF-only optimizer cannot replace that import stage. `gltf-transform` may later optimize already exported glTF, but is not required or silently introduced as a runtime dependency. The [official CLI](https://docs.blender.org/manual/en/latest/advanced/command_line/arguments.html) documents background operation, disabled automatic Python execution, script invocation and a nonzero Python-error exit code; argument order matters. The maintained exporter controls source loading with embedded auto-execution disabled. Never run scripts embedded in a downloaded project/archive.

Provide a versioned local preparation entry point under `scripts/models/` that accepts source path, output directory and explicit profile/config. It records the actual supported Blender version, script revision and complete parameters. The tooling implementation installs/configures a compatible Blender executable or reports a concrete environment failure; it must not ask the owner to choose Blender versus an incapable source importer again. Do not claim a binary is installed merely because this contract chooses it.

Before modifying an asset, record source/archive SHA-256, selected source URL/creator/licence, supplied notices, file inventory, node/mesh/triangle/material counts, texture dimensions, bounds and orientation. Keep original source or its verified manifest outside the shipped bundle. Extract nested archives as data with confined paths; the exporter runs only the maintained project script. For `.blend` loading, disable source scripts/drivers under the supported API as well as CLI policy. A recorded local Downloads path is intake evidence, never a runtime URL or proof that another checkout has the source.

The initial output profile is **static mesh plus explicitly named parts**, packaged as a validated self-contained GLB and plain manifest. Bake static hierarchy transforms, normalize the logical object to its documented unit bounds/pivot, preserve normals/UVs and retain only explicitly declared moving part mounts. One primary mesh may contain material groups; additional flat mesh parts have stable opaque node references/local transforms and optional authored pivot metadata. No arbitrary skeleton, source scripts, hidden cameras/lights or animation clips enter this profile. Unsupported content fails with an actionable processing report, not a half-loaded model. Use ordinary embedded textures and geometry initially; do not require Draco/KTX decoder downloads or external source URLs at runtime.

Retain the existing starting budgets: 2,000 triangles, two material slots and textures at most 512×512 per repeated logical object, adjustable with measured silhouette/readability evidence. Simplify/bake only as needed; thin hat folds, fan blades and die face markings require inspection rather than blind decimation. Record before/after counts, modifications, color-space/normal/roughness choices and tool parameters. The manifest includes overall bounds, primary/part references, source and processed revision/checksum, texture/material inventory, credits/notice paths and any explicit budget exception. Do not infer a part’s animation from its name: definitions bind a role to a node reference and registered behavior.

Every distributed asset/adaptation retains the recorded source/creator/licence/modification information and upstream notices under the existing credits process. The importing PR moves the matching `CREDITS.md` entry from Selected, pending to Shipped with actual paths and modifications. Do not copy a claimed licence from a source filename or treat this architecture decision as provenance verification. D20’s recorded ShareAlike requirement remains its asset task’s explicit distribution check; unrelated code licensing is not changed here.

## Prepared asset provider and cache

Use the **installed Three.js GLTFLoader add-on**, not a second rendering library. The [official loader documentation](https://threejs.org/docs/pages/GLTFLoader.html) describes the explicit add-on import and asynchronous load/parse API. Register a provider for the validated static-parts profile. The definition supplies an asset/manifest handle and revision; the provider never chooses from a material/item identity table or guesses an effect from a filename.

A renderer-context-owned cache coalesces preparation for the same asset revision/profile. Its entry owns the parsed immutable geometry/textures/base materials, validation metadata, pending request and reference count. Consumers receive a prepared blueprint lease, not ownership of the shared buffers. Different rendering contexts cannot share mutable capture/environment targets. Raw file bytes may use ordinary transport caching; no cross-context render target or global mutable “current model” is allowed.

Fetch only the bundled self-contained asset and validate the profile/manifest before exposing a ready handle. A cancellable fetch may feed `parseAsync`; do not promise that a loader promise itself can abort parsing. When the last consumer leaves during preparation, cancel what can be cancelled; a late parse completion with no live consumers must dispose its results rather than mount. Concurrent consumers retain their own leases; cancelling one does not abort another’s valid preparation. Failure removes or marks the failed entry with explicit retry semantics, keeps the declared fallback and reports a diagnostic. No permanent unresolved promise can hold input or a result scope open.

The cache releases parsed geometry, texture and decoded-image resources under the provider’s ownership contract when its last lease/context ends. An instance never disposes another instance’s shared geometry or texture. Per-instance stateful material clones/feedback bindings are explicitly owned and released with that instance; immutable textures/program source remain shared. Verify release against the loader’s decoded-image resources rather than relying only on scene removal. Cache keys are resource/revision/context handles, never behavioral tables keyed by a material name.

## Registered adapters for current visual interfaces

`PassiveVisual` and `BlockAppearance` currently supply primary geometry/materials plus flat extras, not arbitrary glTF scene roots. Adapt the prepared static-parts profile to those existing shared builders instead of rewriting every host to understand a model hierarchy. A registered imported-model factory supplies normalized primary geometry, explicit additional meshes, whole-object bounds, pick/outline geometry and named part mounts. Passive definitions select it through `visual.builder/config`; material appearances select their registered assembly/config. The same definition and adapter are consumed by rack, shop, inspector/browser, hand and field as applicable. A second model is another asset/config, not another renderer.

Loading is a presentation preparation capability: a definition also supplies its current-artwork fallback. Prepare asynchronously, then swap the **appearance channel** through the generation/revision-checked mount/projection contract, preserving pose, input ownership and captured interaction state. The existing mount registry (#1163) provides opaque channels/leases; it does not itself free GPU assets or make these builders asynchronous. The adapter owns that preparation/binding bridge. Source removal/scene exit invalidates the pending consumer; a late model cannot replace a new occupant or resurrect a card. Restore renders the current definition without replaying activation/model commands.

All visual instances use a uniform owned-resource/disposal capability. `PassiveVisual.dispose` already supplies a seam; the card adapter must replace blind disposal of shared imported geometry with the same explicit ownership handoff, applied uniformly through the appearance builder rather than `if imported` checks. Existing procedural builders keep their current owned-resource cleanup. Imported instances release cache leases and their own material clones/part transforms, never the cached asset prematurely. Extend this normalized lifetime interface in the shared builder/consumer, not via per-host special cases.

Rebind the declared selection/activation/transition feedback to the newly prepared appearance and reapply the current presentation state without restarting gameplay. Use [appearance-owned selection feedback](game-architecture.md#appearance-owned-selection-feedback-1153); a GLB material is not evidence that every generic caller can write `emissive`. Registered prepasses belong to the host as usual. Supplemental geometry participates in bounds, hit testing, outline/feedback and disposal; an invisible pick proxy is never rendered as a surrounding cube. No extra logical cells, altered mass or collision rules follow from asset detail.

For moving parts, a separately registered part-animation capability takes an opaque part mount, axis, pivot, speed and reduced-motion policy from the definition. It advances on the shared ambient presentation frame/clock, not a new timer or finite scheduler queue. Air’s selected two fan units share prepared resources; only configured rotor mounts spin at the already documented initial 1 revolution/second, while housing stays fixed. A source containing only one mesh does not prove separable rotors: offline processing must author/verify the parts or record the permitted faithful reconstruction. No visual factory tests a node name to decide it is a fan.

## Asset-specific adoption stays focused

After reusable tooling/provider/adapters merge, each selected asset ticket delivers its processed asset and its defined adoption or clearly stated preparation-only scope. Present remains opaque with no rank/suit or contents disclosure; Le Chef is the selected toque without a visible surrounding cube; the white magician hat retains the separate progress display; Air keeps its documented opposed-fan/vent composition. These are definition configuration, not exceptions in the model loader.

Dice source preparation and in-game adoption may remain separate focused tickets. Validate source face labels, UVs, normals, opposite-face conventions and actual silhouette before shipping. Imported artwork must not silently reroll a die, change sides/probabilities or rename the saved D12-compatible handle. The imported factory uses validated supplied face artwork/metadata rather than repainting faces based on a die identity. A selected-source processing ticket does not prove the game has adopted it; parent tracking must retain the adoption requirement. Unselected models, such as the remaining D8 selection, do not block processing already selected D6/D12/D20 assets.

## Source evidence, alternatives and verification limits

`src/passives.ts:PassiveDefinition.visual` and `src/passive-visual.ts:passiveVisualBuilders/createPassiveVisual` already separate configured visual factories from callers; `PassiveVisual` exposes geometry/materials/extras and dispose. `src/visual/chef-toque.ts` supplies procedural current artwork, not an imported-model loader. `src/visual/block-appearance.ts:BlockAppearance` similarly describes geometry/materials/extras/prepasses; `src/rendered-blocks.ts:dispose` directly disposes owned geometry/material arrays, identifying the shared-resource lifetime seam that must change before cached imported geometry is used. `src/visual-events/mount-registry.ts` supplies pose/appearance revisions and invalidation callbacks but no asset cache. A source search found no GLTFLoader/imported-model builder in these paths. No local Blender or gltf-transform executable was found at this audit; the supplied Present and chef archives were present, while other asset paths require their own availability check.

The existing Three.js add-on is preferred to a new renderer/parser dependency. A constrained flat-parts export profile fits current visual interfaces and the selected static artwork; a general skeletal scene framework would add unrequested scope. Per-item loaders would duplicate cache, cancellation and ownership policy; offline-only procedural approximations would miss the selected-asset request. A placeholder/fallback is useful during preparation but cannot count as completed asset adoption. Official tooling references support API availability, not successful conversion, safe counts or rendering performance for these archives.

Required checks: deterministic profile/manifest validation and actual supported exporter version; no source auto-execution; bounds/normal/UV/texture quality; pending load with two consumers and one cancellation; failure/retry; late completion after exit/removal/revision change; cache/context separation; shared geometry/textures surviving one instance disposal; owned clones disposed once; primary/extras outline/hit/feedback; movement/selection/activation preserved across preparation; all required hosts and reduced motion; production packaging retaining processed assets/credits but excluding source archives/tooling. Supply real source/processed turntables, host screenshots and measured 1/10/50 rendering/resource costs. This docs-only contract contains no invented asset measurements or claim that preparation/cache/adapters are already implemented.
