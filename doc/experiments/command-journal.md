# Committed command journal for verified replay (#1237)

This resolves #936's missing command-capture/refill contract. The existing recorder captures facts, not the inputs needed to reproduce them. Keep setup hydration, explicit setup replay, subsequent player commands and presentation separate. Preserve the [exact-build import boundary](configuration-compatibility.md); a journal does not create portable cross-build replay.

## Model-owned successful command metadata

The authoritative command boundary captures a plain canonical descriptor for the actual command it successfully commits. The bench must not infer a command from facts, a debug trace, state differences, pointer gestures or the call it attempted. Use registered command codecs/handlers keyed by command reference; no generic branch on scene, mode, item or material. Extract/reuse the ordinary command vocabulary behind scenario replay without importing Dev setup policy into the model.

Extend the existing `onCommitted` callback compatibly: its first argument remains the ordered immutable fact array; a second immutable action metadata value carries action ID, captured run/stage context/version, canonical `{ command, version, args }` descriptor or explicit unavailable reason, and an optional checkpoint projection from the already configured checkpointable random source. Existing one-argument listeners retain their behavior. Metadata shares the transaction's success/rollback boundary, is captured before later callers can mutate args, and publishes only after the entire command mutation commits. It is not a new `lifecycle` event, passive hook, event bus or permission for presentation to issue gameplay commands.

A supported command may commit a state change without emitting gameplay facts (for example a real refill or reorder). Publish its metadata with an empty fact array; recorders must not discard it merely because there is no fact. A refusal, thrown/rolled-back action, duplicate submission or true no-op produces no successful journal step. No-op detection belongs to that command owner/registered result, never a generic before/after state diff. Existing action IDs correlate within a run; use trial-local indexes for comparison rather than requiring identical freshly generated run tokens during verification.

Initial required codecs/executors are `play` (normalized PlayAction), `discard` (ordered card IDs), `refillHand` (empty args), `reorderHand`/`reorderPassive` (validated from/to), and `applyRackItem` (item/card IDs). They call the ordinary model mutation, not input adapters. Each owner captures its own normalized arguments and transaction result. Card/material setup, direct developer mutations, purchases, navigation and future commands need their own declared codec before the artifact claims those steps replayable. Unsupported committed mutation metadata explicitly marks the recording incomplete from that index; never silently omit it and report a successful full replay. This is a bounded initial vocabulary, not an exemption from completeness.

Logical/runtime IDs are encoded through the same validated instance mapping preserved by the initial configuration artifact. The executor resolves those opaque references; IDs never select behavior. No functions, live blocks, handler instances, material objects, textures or private credentials in a descriptor. Validate command-specific schema/version, finite values and existing scenario horizon/size limits before candidate execution.

## Refill is an explicit separate step

Record the actual ordinary `refillHand` mutation as its own successful journal command when it draws/transfers cards. Its state and checkpointed RNG changes use the same atomic transaction boundary, with no new passive draw hook implied. It has zero awarded score and no scoring-line replay. A terminal/full hand that performs no mutation creates no refill step. The live controller still decides **when** its configured ordinary after-action refill runs; journaling does not move that policy into the recorder or renderer.

Verified journal execution of `play` or `discard` performs that primitive command only. It does not implicitly call refill: the next recorded refill step does so exactly once at its original position. Preserve existing scenario `devReplay` semantics through a separate composite adapter that explicitly invokes primitive play/discard then ordinary refill. Existing setup recipes therefore keep their declared after-action behavior; do not globally change the meaning of their versioned commands to fix the new journal. New journal and setup replay paths share the primitive executor/validation, not a hidden refill side effect.

This distinguishes a caller's successful play from its subsequent refill and captures their actual ordering if other mutations occur between them. It also keeps the journal faithful while the model-first refill migration (#1165) changes its controller owner. A replayed command never calls a UI callback that performs an extra refill. Any command whose implementation already owns an atomic compound mutation must declare that in its codec version instead of recording an invented extra transfer.

## Recorder, provenance and verification

Publish experiment-record **version 2** for command-bearing entries. Each chronological entry contains command metadata, ordered captured facts, actual awarded delta/current score, applicable metrics and optional model-RNG checkpoint. An empty-fact refill/reorder has zero awarded delta, no counterfactual scoring rows, and its own action identity; do not reuse the last play's scored lines. Parameter changes/trial boundaries retain their explicit ordered records. Version-1 fact-only records remain inspectable as evidence but are not silently upgraded to verified replay by guessing commands.

The complete replay artifact combines a versioned outer format, the validated configuration/provenance artifact (#934), the command-bearing record, explicit setup-command provenance and compatibility diagnostics. Export whether commands/checkpoints/initial state are complete. Preserve the actual generated initial card/passive descriptors, logical ID mappings, effective rules/settings, setup replay and **starting** random state/cursor from the installed trial, not a newly sampled seed or the current random cursor substituted as the beginning. The trusted caller still supplies the actual immutable build identity. Unknown provenance/checkpoint/source support makes verified replay unavailable while JSON inspection/export can remain available; never claim determinism from seed alone.

Reconstruction and comparison run off to the side. Validate exact build/schema/command bounds and completeness before allocating the candidate; construct the captured initial trial and execute only the explicitly recorded setup list once, then start player journal execution at its declared post-setup checkpoint. Do not replay setup effects twice during adoption or reset live trial state. Restore captured checkpointable randomness through its existing validated API, not a global RNG override. If the installed trial record begins mid-session without a complete reproducible starting snapshot/checkpoint, label it incomplete rather than invent earlier commands.

Compare each step's accepted/refused result, canonical fact sequence/payload, awarded points, score/outcome and configured deterministic state/RNG projections. Normalize only declared correlation fields (fresh run/action IDs mapped by index); do not strip differing gameplay facts to get a match. Float tolerances, if needed for measured geometry, belong to named projection codecs; exact integer economy/score/IDs remain exact. Report the first mismatch with index, command, expected/actual projection and bounded diagnostic. The candidate is disposed on success/failure, with no audio, live scene subscriptions, rewards to the live run or mutation of its state/RNG. Model responses within the isolated candidate are legitimate replay, not hydration effects.

## Evidence and delivery slices

Audit at `1a320fd`: `src/experiment-recorder.ts` subscribes to `onCommitted`, discards empty arrays and stores facts/metrics; it has no command descriptor. `src/lifecycle/action.ts:EventEnvelope` correlates facts but does not encode input. `src/game-run.ts:play/discard` have action transactions; `refillHand`, hand/rack reorder and some direct methods do not all share that boundary yet. `src/dev-scenario.ts:scenarioReplayCommands` registers play/discard through `refilled`, which calls `run.refillHand` after success. `src/action-log.ts` is a bounded input/debug trace, not an authoritative journal. These source facts support separate primitive metadata and explicit refill rather than replaying guessed UI actions. The design does not claim every listed command owner is already transactional.

A bench-side attempt log can include rejected inputs and miss autonomous/model commands. Recording only facts cannot reconstruct placement arguments. Reusing the setup replay handler unchanged would refill twice once explicit refill steps are recorded. A global all-command migration is larger than this initial supported vocabulary. Compatible commit metadata plus registered codecs makes missing support explicit and permits focused owner adoption without weakening verified replay.

Separate runtime slices: (1) metadata/codec boundary and play/discard capture; (2) transactional refill and its descriptor; (3) reorder/item-use command capture for admitted trial inputs; (4) version-2 recorder/provenance; then #936's artifact/executor/comparison consumes those capabilities. Each follows this separately merged contract. The existing setup adapter remains tested; #937's UI composes the finished export and reports unavailable/incomplete provenance rather than making up a build identity.

Verify normalized args survive later mutation; no metadata for reject/throw/no-op/duplicate; facts and metadata correlate including empty-fact commands; atomic state/RNG rollback; live versus recorded refill order and no double refill; reordered rack changes later response order identically; item uses/counters; unsupported mutation and legacy v1 diagnostics; exact-build and missing starting checkpoint rejection before candidate construction; setup executed once; mid-trial missing provenance; same-build deterministic replay of multiple play/discard/refill sequences; first mismatch and bounded input; differing generated run tokens normalized without hiding facts; and zero mutation/audio/RNG change to the live trial. No replay correctness or browser acceptance is asserted by this documentation alone.
