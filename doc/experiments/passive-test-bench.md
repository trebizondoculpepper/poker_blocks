# Passive scenario test bench

Owner-approved target, 2026-11-13 (#867, room #820). This is an interactive balance test bench, not a set of fixed showcase examples. It lets the designer try provisional rules in controlled, rather abstract situations, observe how they feel and what actually happens, and then use the evidence to guide broader playtesting and balance. Repeatable scenarios complement automated correctness tests; they do not prove full-run balance or certify a modifier automatically.

## Scenario composition and controller

Compose a DevScenarioController into the experimental room. It coordinates separately registered capabilities for deck building, starting hand selection, passive installation/configuration, initial field arrangement, optional command replay, live measurement and export. Testing-only capabilities use Dev-prefixed trait names. Definitions, setup and services do not learn the room identity. A selector chooses a scenario definition by opaque handle; its registered capabilities and configuration determine behavior. No giant scenario switch or per-passive control code belongs in the host.

A scenario definition is versioned plain configuration: display metadata, seed, builder reference and effective options, ordered hand selectors, ordered passive descriptors with settings, field placements, optional explicit replay commands and selected measurement providers. References resolve through registries; registry IDs are lookup handles, not a side table that defines room-specific behavior. The deck-building capability reuses deck-builders.md and #827, including weighted composition, without a second experimental deck factory. A hand selector identifies created logical instances/indices deterministically; duplicate rank/suit content never means duplicate instance identity.

The controller validates the entire definition and constructs a candidate initial run off to the side using registered factories/zone transfers and initial-state hydration commands. Validate known capabilities/config versions, finite counts/coordinates/parameters, unique logical/runtime IDs, exactly one live owner per instance, allowed initial zones, admitted provisional content and valid passive/rack capacity. Declare input-size limits through configuration and reject oversize scenarios deterministically before allocation. Publish the new run and subscribe presenters only after all setup succeeds. Invalid configuration leaves the current trial intact with an inspectable diagnostic.

This controller owns experiment setup policy, not a second set of game rules. Once a trial begins, normal registered gameplay commands/dealer rules resolve moves. Controller-driven fixture setup may construct an explicitly labelled state that would be expensive to reach manually, but it must still satisfy ownership/schema invariants. Default initial layouts respect ordinary spatial constraints; unusual fixture permissions must be explicitly configured and displayed, never inferred from dev-room identity.

## Hydration is not replay

Two separate capabilities are required:

- Initial-pattern hydration places the declared existing cards directly into their starting zones/field as one validated setup. It consumes no plays, scores nothing, triggers no placement reactions, awards nothing and emits no historical audio/visual events. This is starting state, like restore, not a shortcut through normal play.
- Command replay is an optional declared ordered list of actual validated gameplay commands after the initial snapshot. It DOES consume allowances, score, trigger passives/reactions and advance model RNG exactly as normal play. Failure rejects the candidate trial setup atomically; do not silently skip illegal commands. Records distinguish configured fixture state from effects caused by replay.

A scenario must never imply normal placement effects by accidentally calling the live UI drop handler during hydration. Captured commands and initial state are exported separately, so a reviewer can tell whether a warmed material was supplied as a fixture or created by an action. Do not replay effects while restoring a saved trial.

## Reusable configurable-passive capability

Implement a reusable configurablePassive capability on eligible definitions; it is not Dev-prefixed because a future normal-game feature may legitimately use instance configuration. It provides registered schema/validation, default parameter data, effective-rule construction and a public effective-settings description. A passive instance owns its overrides. Shared definitions stay immutable; no new global definition is registered for every slider combination, no identity string encodes parameter values, and one copy's overrides never alter another copy.

The declared schema names the adjustable parameters and their permitted types/ranges. Initial schemas cover existing trial curve parameters and aggregate selection already exposed by the trial definitions. Resolve definition defaults plus explicitly supplied named parameter overrides; reject unknown keys, unsupported schema versions and invalid combinations. Reuse scoreCurves/validateQueryFactor validators and registered aggregate/query configuration. Do not accept arbitrary replacement eventRules or an arbitrary deep merge that bypasses definition policy. A definition without this capability simply has no adjustable controls; the registry supplies a fixed-rule provider, rather than generic UI/scoring checking a trait flag.

At instance composition, the registered effective-rule builder produces that instance's ordinary passive.eventRules from validated effective configuration. Existing generic event/scoring dispatch consumes those rules uniformly. Capture resolved parameters in action outcomes/activation descriptors; delayed visuals never consult newer settings. Settings description and slider inputs derive from the capability's schema, not a hard-coded dense/heavy/material-name branch. Expose real controls and keyboard labels through the bench's composed panel host.

Persist a versioned parameter descriptor through the existing SavedRackItem.traits/configurablePassive entry and rackTraitPersistence registry. The descriptor contains schemaVersion plus overrides only; effective rules/functions are rebuilt through the validated capability on hydration, not serialized as code. Add this optional trait record without changing existing rack-item shapes or weakening old save validation. Legacy instances with no overrides use definition defaults; unknown/invalid versions fail explicitly. Exact clones copy independent overrides; reset/reset-clone uses the definition's declared baseline through existing reset facets. Current normal definitions need no new overrides or behavioral changes.

## Selecting trials and changing settings

Registered scenario setup installs the explicitly ordered passive descriptors with fresh IDs and effective settings before initial state publication. The Dev controller coordinates those setup steps; it does not push passives into a rack through ad hoc direct state writes. Use explicit experimental catalogue access and the registered public contributions: provisional content is visibly marked, while certified content has no public certification notice. Provisional definitions remain absent from ordinary shops.

Default parameter-change behavior is a full trial restart from the SAME initial scenario and seed, with the new effective parameter values. Clear previous scores/uses, recreate a fresh run, replay only the scenario's explicitly declared setup-command sequence, and begin a new trial ID. This supports clean A/B comparisons and avoids pretending previous accumulated scores used the new curve. Ordinary user moves are not automatically replayed unless a separate explicit replay request uses their recorded log. Cancel the old visual generation/scopes before binding new presenters. Reject invalid edits without destroying the old trial. Do not allow a half-applied slider value to mutate a committed action.

Use an explicit Apply/Restart action rather than restarting on every keystroke. A fresh-seed/new-run action is separate and records the actual new seed. User-selected scenarios may vary deck properties, passives and starting patterns independently. Initial bench controls can be text/numeric/dropdown panels; new decorative artwork is not a prerequisite for useful balance experiments. Existing input owners handle controls, with the configured UI action sound once per confirmed change, not per readout frame.

## Measurement, export and lifecycle

Reuse the already documented pure snapshot queries and activation outcomes. Display effective scenario/settings, trial/seed identifiers, packing/mass/material metrics, score and actual applied contributions. Readouts consume committed snapshots/facts and do not infer effects by diffing render state. An unavailable metric is visibly unavailable, not a numeric zero. Non-scoring fixture context remains distinguishable from scoring contributors.

#821 exports a versioned local configuration plus complete replay/result evidence: scenario/builder versions and seed, actual initial logical card/passive descriptors, per-instance overrides, zones/field layout, explicit setup commands, subsequent player commands, outcomes and parameter-change trial boundaries. Reuse existing card/rack codecs and their validation; keep IDs unique and do not maintain a second authoritative live inventory. Configuration-only export and complete evidence export are different products; full internal replay data may disclose future draws/opaque contents and must not appear in ordinary inspection. No credentials or remote telemetry. Unsupported imports reject atomically. The [bounded configuration compatibility contract](configuration-compatibility.md) requires an explicit matching immutable build identity before verified import; source provenance plus a partial settings list does not establish cross-build equivalence.

Entering/resetting restores subscriptions and poses once, without old model facts or audio replay. Cover/pause follows the host contract. Exit cancels setup work, removes subscriptions/readouts, disposes trial rendering and invalidates old scheduled callbacks. Model actions remain immediate; finite feedback uses the shared scheduler and ambient animation stays per frame. Normal gameplay, saved runs and global catalogue configuration remain untouched by a bench trial.

## Evidence, alternatives and verification

src/run-setup.ts supplies registered setup passes; deck-builders.md documents the composable generation adapter. src/passives.ts:createPassiveBlock currently copies definition.eventRules onto the passive instance; this is the seam for validated instance-specific rule construction, not a requirement for the scorer to check overrides. src/trial-modifiers.ts has registered curves and validateQueryFactor, but its current exported parameter constants are definition defaults rather than editable instance state. src/save.ts:SavedRackItem and rackTraitPersistence already provide named optional trait codecs. The ordered ownership, clone/reset and gameplay lifecycle documents supply hydration and immutable-command boundaries. These are inspectable source/contract foundations; the scenario controller and configurablePassive are still new work.

Runtime-generated definitions per slider position would accumulate registry identities and complicate saves/reproduction; fixed build-time parameters would not provide the requested interactive bench. Validated per-instance configuration plus a scenario controller is chosen to keep behavior reusable and copies independent. A full restart on Apply is the initial engineering default, chosen for clean comparable trials; later live editing needs its own explicit model command semantics.

Verify instance isolation/default preservation, unknown/invalid parameters, schema-derived controls, effective-rule/outcome agreement, optional codec round trip and legacy saves, clone/reset independence, atomic bad scenarios, ownership/duplicate content, fixture hydration silence versus real replay effects, deterministic same-seed restart, failed replay rollback/RNG, exported setup/action distinction, repeated enter/exit and no provisional leakage. Bench trials guide decisions; they do not establish production power or topology algorithms.
