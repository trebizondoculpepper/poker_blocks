# Heat adjacency and single-source Cloud generation

Owner rules #1268, documentation #1384, 2026-11-15. This supersedes the old requirement for Air beside Boiling Water to make a Cloud. Steam and Cloud are the same existing card/material. No new material, score multiplier or production Water artwork is introduced by these rules.

## Heating and authored source strength

Water reads only **six face-neighbours** for heat. One ordinary Fire/Flame heats it to existing Hot Water (`heated`, +1 when contributing). Two ordinary Fires, or one Aggressive Fire, boil it (`boiled`, ×2 when contributing, replacing the previous state bonus). A mixture at least as strong also boils. Boiling takes priority over heating; neither hot nor boiling water cools automatically. Ordinary fire cannot downgrade boiling water. An unchanged state is a no-op with no duplicate transition fact/sound.

Air sharing a face with ordinary Fire still stokes it into Aggressive Fire in the existing pre-scoring phase. Air is not an input to Water or Cloud creation. Fire and Water are not consumed by heating or cloud generation. Other heat/cooking/melting rules retain their existing documented semantics; this change does not make every hot material an extra Fire source.

**Reusable target:** quantitative heat-source behavior brings registered pure contributions to a snapshot query. Ordinary Flame contributes authored strength 1; its aggressive state composes an additional strength 1, so that card contributes 2. The Water definition configures threshold reactions against the summed face-neighbour strength: at least 2 → boiled, at least 1 → heated, subject to the existing non-downgrade/no-op rules. Put these numbers/commands on their source/target composition, not a material-name lookup table or an `if aggressive` branch in a generic engine. Definition/state composition owns the contribution; a trait read as a Boolean marker is not an implementation. The query is pure, requested on the step snapshot, and must not publish facts or allocate a new effect per neighbour.

Existing generic matcher/result registries remain the reaction dispatch seam. Extend with a registered heat-total query/matcher and source contribution contract rather than hard-code the number of Fire neighbours. No new temperature simulation, cooling timer, continuous real-time damage or unbounded equilibrium loop is approved.

## One Cloud per Boiling Water source per committed play

At the ordinary post-score material step, each source that is **already boiling in that step's frozen snapshot** may produce one Cloud. Water that first boils in this post-score step starts producing on the next committed play; this preserves [phase snapshot semantics](material-phases.md). A pre-score change can be visible to the later snapshot as already documented. No Cloud from a discard, rejected action, inspection, load or animation tick.

Eligible destinations are all empty grid cells with offsets in `{-1,0,1}³` excluding `(0,0,0)`: **26 face, edge and corner neighbours**. This wider spawning neighbourhood does not widen six-face heating/stoking/cooking. If no candidate is free, nothing spawns and no selection/rank/suit randomness is consumed. If candidates exist, choose uniformly with the run's model-owned seeded RNG, then choose rank and suit independently/uniformly from the existing configured standard card pools. Do not inherit the source's rank, suit or acquired bonuses, add a wildcard, or bias toward higher scoring lines. Even a single eligible cell uses the defined destination draw so successful spawns have the same explicit destination/rank/suit draw sequence; tests record that sequence.

Process source plans in lexicographic `(x,y,z)` cell order; a unique cell makes a further identity tie unnecessary. Enumerate offsets in the same stable lexicographic order. Candidate occupancy is the step snapshot plus reserved earlier spawn destinations. Exclude snapshot-occupied cells even if another planned consequence would vacate one in this step, and reserve each selected destination before the next source chooses. This resolves two sources competing for a gap without traversal-order accidents. New clouds are not rescanned as new sources in the same step. This is a reversible deterministic resolution default, not a new player objective.

Create the Cloud through the existing generated-card/adoption command path, unique live instance identity and stage/table-only retention; it never silently joins the deck. Validate all plans and commit state/RNG/facts atomically under existing action budgets. Any failure rolls back the entire action; do not publish successful partial births. Restore reconstitutes saved state without rerunning generation. The committed generated-card fact carries captured identity/material/cell/source for presentation and the existing `reaction.condense` cue once per actual birth. Change that sound's description to the new trigger during implementation; no sound on blocked/no-op births and no new duplicate transition sound. Visual bubble/refraction work is independent (#676/#1015).

## Source audit, alternatives and limits

Audited main `5fb25a93`: `src/reactions.ts:Reaction`, `reactionMatchers`, `reactionResults`, phase selection and command collection already separate definition configuration and snapshot matching from command commit. Current neighbour material/state matchers test presence, not quantitative source strength. `src/materials.ts` configures one ordinary Flame heating and aggressive Flame boiling. The source/state quantitative contribution is therefore a new explicit capability, not something the current matchers already provide.

`src/pair-spawn.ts` registers `spawn-beyond-pair`, selects Air/boiling partners, considers two shared-axis ends, compares candidate scores, and inherits an input-derived rank/suit. That algorithm contradicts every changed single-source/random-placement rule above and must not be cosmetically renamed. A reusable configured `spawn-near-source` command/result should take source identity, destination-neighbourhood reference, output definition reference, identity-generation recipe and retention/adoption capability. Generic code resolves registrations, not material identities. Remove the old Air pairing from its definition composition; do not delete generic pair-spawn machinery solely because this one use changes.

`src/rule-commands.ts:CommandTarget` already supplies the transaction's model RNG; generated-card ownership and phase budgets are documented in ordered-card-ownership.md/game-events.md. `src/pair-spawn.test.ts`, `src/reactions.test.ts`, `src/material-scoring.test.ts` and state/ownership tests are reusable fixture evidence, not proof that the new rules work. The former score-maximizing destination and inherited identity are explicitly superseded; keeping them would fail the owner's request even if existing tests pass.

A duplicated Fire-count special case would prevent future composed heat behavior. A separate real-time Cloud timer would violate committed-play cadence/restoration. Choosing all positions simultaneously without reservations would permit collisions. The selected snapshot/contribution/command approach preserves shared lifecycle, atomicity and deterministic game randomness. No new runtime probe or performance measurement was executed for this design.
